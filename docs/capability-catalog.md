## How a contract works

An assistant never calls a Twake application. Each action it may take is a contract: one HTTP operation of the contracts service, published in its OpenAPI document and declared as a route in APISIX. The harness turns each operation of that document into a tool.

```
harness tool --apikey, x-twake-on-behalf-of--> APISIX --Bearer (owner)--> contracts service --as the owner--> application
                                                  |
                                                  +- key-auth and consumer restriction
                                                  +- forward-auth: the token broker returns the owner's access token
                                                  +- oas-validator: the request matches the contract
                                                  +- http-logger: one audit record per call
```

- **Names.** The contract id is the operation's first tag, a versioned dotted name `<domain>.<object>.<verb>.v1`, such as `calendar.invitation.accept.v1`. The tool name is the operation's `operationId`, a verb such as `accept_invitation`. Paths live under `/contracts/v1/<domain>/`.
- **Reading and writing.** A `GET` contract reads; any other method writes. Today the harness requires the action `contracts.call` for the first and `contracts.act` for the second, and withholds `contracts.act` from turns that an event started ([`src/contracts/tools.ts`](../src/contracts/tools.ts), [`src/agent/tools.ts`](../src/agent/tools.ts)).
- **Identity.** The harness names the owner in `x-twake-on-behalf-of`. APISIX hands that email to the [token broker](https://github.com/linagora/twake-space-token-broker/tree/7ec6929), which returns the owner's access token, and passes the token on. The contracts service takes the user from the token alone. The owner is never a contract parameter, and the harness never holds a token.
- **Rules the existing contracts follow**, which every new one keeps ([contracts README](https://github.com/linagora/twake-space-agent-contracts/blob/3fce060/README.md)):
  - one narrow operation per tool, never a generic proxy to the application;
  - something the owner cannot see answers exactly like something that does not exist (404);
  - inputs are bounded: lists of 1 to 100 items, periods of at most 31 days;
  - an ambiguous case is refused with a typed [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) problem rather than guessed, as a recurring invitation is.
- **Rules this catalog adds:**
  - text that other people wrote (a mail body, an event description, a file, a task, a message) comes back in an `untrusted` object, apart from the data the contract computed;
  - every write declares `x-twake-risk` (`low` or `high`) in the OpenAPI document; a write without it counts as `high`;
  - a contract that makes the application notify other people says so in its description, so that the model can tell the owner;
  - every operation's description gives a worked call, with values in their exact format, as [`read_freebusy`](https://github.com/linagora/twake-space-agent-contracts/blob/3fce060/src/twake_space_agent_contracts/freebusy.py) has done since a demo in which the model sent times that APISIX's OpenAPI check refused.

## Decisions

Taken on 2026-10-06 by the product owner, on the research below.

| Topic         | Decision                                                                                                                                                                                                                                                                              |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tokens, pilot | The broker's token gets the audience of each application that checks one, as `tcalendar` already does for Calendar: `twakemail` for Mail, `twaketasks` and the claims it needs for Tasks. Drive and Chat need their own exchange. One token per application is the production target. |
| Consent       | Nothing is granted by default. On the first use of an application for reading, or for writing, the harness asks the owner in the chat.                                                                                                                                                |
| Answer        | The owner answers with a ✅ or ❌ reaction on the request, or with an exact yes or no message right after it. The harness reads the answer itself: the model never decides that the owner agreed, and no other member of the room can answer.                                         |
| Writes        | A write consent covers ordinary writes. A contract marked `x-twake-risk: high` is confirmed one call at a time, on the frozen call, and capped per user in APISIX.                                                                                                                    |
| Event turns   | When an event needs a first use, such as an invitation that requires reading the calendar, the assistant asks with that context and resumes after the yes.                                                                                                                            |
| Tools         | The model sees the tools of every deployed contract, and consent is checked when a tool is called. Past about 40 tools, the harness moves to one entry tool per application.                                                                                                          |
| APISIX        | Contracts are declared per application, with the upstream and the OpenAPI address given once.                                                                                                                                                                                         |
| Mail          | Moving, archiving and trashing are first-wave writes. Spam reports are a separate high-risk contract; their risk class is a product decision to revisit.                                                                                                                              |

Defaults taken with them:

- One contracts service, with one module per application. The harness reads a single OpenAPI document (`CONTRACTS_OPENAPI_PATH`), and the service already handles token checks, problems and signing keys.
- Existing assistants keep Calendar read and write, so the running pilot needs no new consent.
- The `events` domain, the assistant's own feed of workplace events, is granted for reading.
- A consent lasts until the owner withdraws it. The owner may withdraw one through the model, never grant one.

## Consent and approval

### What the owner sees

The harness speaks the owner's language; the examples are in English.

```
Owner: what did Paul send me yesterday?

Assistant: This is the first time I need Twake Mail.
  Read: list, search and read your mail
  Do you allow it? React with ✅ or answer "yes".

Owner: yes
```

The harness records Mail for reading, replays the frozen `search_emails` call, and the answer follows in the same thread. The first write in Mail asks again, for writing. A high-risk act always shows what it is about to do, even after the write consent:

```
Assistant: I am about to send:
  To:      paul.martin@…
  Subject: Re: Budget Q4
  Text:    "Hello Paul, I approve…"
  Answer "yes" to send it.
```

### Rules

- **Levels.** Read covers the `GET` contracts of a domain; write covers all the others. The domain is the first segment of the contract id: `calendar`, `mail`, `drive`, `tasks`, `chat`.
- **Words.** The request names the application and says what the level covers there, in the words that the [contracts service](https://github.com/linagora/twake-space-agent-contracts/blob/2cdcd134b3dd335608cd70bfde777566929c95fa/README.md#applications) publishes for each application in its OpenAPI document (`x-twake-domains`), in English and in French. Since the harness records one consent per application and level, an application's write words cover every write of that application, and a new write there comes with words that name it.
- **Who answers.** Only the owner, by a reaction on the request or an exact yes or no as the next message. Anything else leaves the request pending. A contract that writes as the owner in Chat never targets a room where an assistant is a member, so no contract can answer in the owner's place (see [Chat](#chat-twake-chat)).
- **The frozen call.** When it asks, the harness stores the exact call (contract and arguments). After the yes, it runs that call, not a new one written by the model, and the turn goes on with its result.
- **Event turns.** A turn that an event started asks with the event's context and resumes after the yes. It never writes without one.
- **High risk.** Each call is confirmed on its own, whatever consents exist. APISIX caps these routes per user.
- **Withdrawal.** The owner can withdraw a consent at any time. The harness then refuses the domain's tools for that level until a new consent.

### What the harness must build

- A consent store per principal (domain, level, time, the request it answered), under the same row-level security as the rest of the owner's data.
- A check at call time: domain from the contract id, level from the method, risk from `x-twake-risk`. It refines today's global `contracts.call` and `contracts.act`.
- A store of pending calls: the frozen call, why it waits (consent or high risk), the request message, an expiry.
- An answer reader in the Matrix role: reactions and exact replies from the owner on a pending request, decided without the model.
- A resume path for both the conversation and the event processing.
- `x-twake-risk` read from the OpenAPI document ([`src/contracts/openapi.ts`](../src/contracts/openapi.ts)).
- A migration that gives existing principals Calendar read and write, and every principal `events` read.

## Tokens per application

| Application | How it checks the caller                                                                                                            | Broker's token today                                                    | Pilot                                                                               | Production target               |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------- |
| Calendar    | Introspection at LemonLDAP; `aud` must contain `tcalendar`; user from `email`                                                       | Accepted: `tcalendar` is an additional audience of `twake-space-agents` | Nothing                                                                             | A Calendar-only token           |
| Mail        | Introspection; `aud` must contain `twakemail` or `teammail-mobile`; user from `email`                                               | Refused                                                                 | Add `twakemail`; userinfo must return `email`                                       | A Mail-only token               |
| Tasks       | Introspection by `twaketasks-backend` (`aud` must contain `twaketasks`), then userinfo with `sub`, `sid`, `uuid`, `email`, `org_id` | Refused                                                                 | Add `twaketasks`; release `uuid` and `org_id`; same `sub` attribute on both clients | A Tasks-only token              |
| Drive       | cozy-stack tokens only, issued by the owner's instance                                                                              | Refused                                                                 | See [Drive](#drive-twake-drive)                                                     | See [Drive](#drive-twake-drive) |
| Chat        | Matrix tokens only (Synapse and ToM)                                                                                                | Refused                                                                 | See [Chat](#chat-twake-chat)                                                        | See [Chat](#chat-twake-chat)    |

What the deployed LemonLDAP-NG can and cannot do. The portal image is [llng-docker v2.21.6-1](https://github.com/guimard/llng-docker/tree/v2.21.6-1), LemonLDAP-NG 2.21 with patches:

- **Additional audiences** are a fixed list per client. Every token of the client carries all of them, and a change applies only to tokens issued afterwards. The broker keeps a token until 5 minutes before it expires, up to 10 hours, so a new audience may take that long to appear ([`getAudiences`](https://gitlab.ow2.org/lemonldap-ng/lemonldap-ng/-/blob/v2.21.6/lemonldap-ng-portal/lib/Lemonldap/NG/Portal/Lib/OpenIDConnect.pm#L2763-2775)).
- **Introspection returns `aud`** on dev thanks to the image's [`717-introspection.patch`](https://github.com/guimard/llng-docker/blob/v2.21.6-1/portal/717-introspection.patch); it is native upstream from 2.22.0. Calendar, Mail and Tasks rely on it.
- **A refresh token works only for its own client**, and a refresh cannot narrow the audience or the scope ([Issuer/OpenIDConnect.pm](https://gitlab.ow2.org/lemonldap-ng/lemonldap-ng/-/blob/v2.21.6/lemonldap-ng-portal/lib/Lemonldap/NG/Portal/Issuer/OpenIDConnect.pm#L1990-2087)).
- **The internal token exchange** ([RFC 8693](https://www.rfc-editor.org/rfc/rfc8693)) looks unusable with the broker's tokens: it finds the user through `user_session_id`, which tokens refreshed from an offline session do not carry ([OIDCInternalTokenExchange.pm](https://gitlab.ow2.org/lemonldap-ng/lemonldap-ng/-/blob/v2.21.6/lemonldap-ng-portal/lib/Lemonldap/NG/Portal/Plugins/OIDCInternalTokenExchange.pm)). This comes from reading the code and needs a test.
- **Resource indicators** ([RFC 8707](https://www.rfc-editor.org/rfc/rfc8707)), which would let one client ask for one audience at a time, need LemonLDAP-NG 2.23.2 or later with the [`oidc-resource-indicators`](https://github.com/linagora/lemonldap-ng-plugins/tree/786afa5/plugins/oidc-resource-indicators) plugin.

With the pilot's cumulative audiences, a token sent to one application is valid at the others for its whole lifetime. Shorter access tokens for `twake-space-agents`, such as 15 minutes, narrow that window. Two production designs remove it:

1. **One client per application** (`twake-space-agents-mail`, `-tasks`, `-calendar`), each carrying only its application's audience. The broker gets one offline refresh token per client during the same consent: after the first login, the other authorizations should pass silently, which remains to be verified. APISIX's forward-auth returns the token each route declares. No LemonLDAP code is needed.
2. **After an upgrade to LemonLDAP-NG 2.23.2 or later**: one client, with `resource` at each refresh.

## Enabling an application end to end

What opening Calendar's free/busy took, and what each application will take:

| #   | Link                            | Where                                                                                                                                                                             | Done                      |
| --- | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| 1   | A token the application accepts | LemonLDAP client `twake-space-agents` (audiences, claims), or an exchange inside the contracts module                                                                             | per application           |
| 2   | The owner's delegation          | Token broker: one consent, the refresh token kept encrypted, forward-auth for APISIX                                                                                              | once                      |
| 3   | The contracts                   | A module of the contracts service: router, client of the application, `<APP>_URL` setting, tests at the HTTP boundary, README section, `x-twake-risk` on every write; a new image | per application           |
| 4   | The routes                      | Deployment repository: the application's entries in the `apisix-contracts` values, the new setting and image digest of the `agent-contracts` release                              | per application           |
| 5   | The tools                       | The harness reads the OpenAPI document every `CONTRACTS_REFRESH_MS` (5 minutes by default): nothing to deploy                                                                     | once                      |
| 6   | Events, for proactive turns     | A producer and a normalizer of the application's events                                                                                                                           | per application, optional |
| 7   | A check end to end              | A test owner's real token through APISIX: the consent question, the call, its audit record                                                                                        | per application           |

Two things must exist before the first contract of a new application is deployed:

- **The harness's consent and risk handling.** Today every principal gets `contracts.call` and `contracts.act` when it is created ([`src/principals/repository.ts`](../src/principals/repository.ts)). A new contract would therefore be open at once to every assistant whose owner consented at the broker, with no first-use question.
- **A reliable path to the broker's consent.** A call without a delegation answers 401 with the consent link (`delegation_missing` or `delegation_expired`). The harness hands that answer to the model like any other result; it should send the link to the owner itself. The broker's offline session also lasts a fixed time from the consent, 30 days by default in LemonLDAP-NG (the value on dev was not read), after which every owner must consent again. Its duration for `twake-space-agents` is a product choice.

Order and traps:

- Apply APISIX before the new contracts image, or with it. The harness sees new tools as soon as the image publishes them, and without their routes they would answer 404.
- APISIX caches the OpenAPI document for an hour by address. Give it a new address with every image digest, as `?image=<digest>`, and with every change of `PUBLISHED_APPS`, so that the new document is fetched.
- Tokens cached by the broker get a new audience only at their next refresh. Restart the broker to apply it at once.
- The contracts service restricts only its ingress; check that the application accepts traffic from the contracts service's namespace.

Switching an application off: the contracts service publishes only the applications that its [`PUBLISHED_APPS`](https://github.com/linagora/twake-space-agent-contracts/blob/2cdcd134b3dd335608cd70bfde777566929c95fa/README.md#applications) setting names, `events` and `calendar` when it is unset or empty, and `events`, the assistant's own feed, whatever it says. It serves and describes their contracts alone, in `x-twake-domains` too, and the paths of any other application answer 404 like a path it never had; a name it does not know stops it from starting. The settings of Mail, Drive, Tasks and Chat, such as `MAIL_URL`, are required once `PUBLISHED_APPS` names their application, and only then. Kept equal to the applications APISIX routes, the setting makes the gateway and the tools move together: take the application out of `PUBLISHED_APPS`, so that its paths answer 404 once the new pods serve, give the OpenAPI document a new address, and its tools leave the agents when the harness next reads the document, within minutes; then remove its routes.

The `apisix-contracts` values, grouped per application as decided. The applier needs to learn `apps` and `risk`; today it takes a flat `contracts` map:

```yaml
contractsOpenapi: http://agent-contracts…/openapi.json?image=<digest>

apps:
  calendar:
    upstream: agent-contracts
    contracts:
      calendar.freebusy.read.v1:
        uris: [/contracts/v1/calendar/freebusy]
        methods: [GET]
  mail:
    upstream: agent-contracts
    contracts:
      mail.emails.read.v1:
        uris: [/contracts/v1/mail/emails, /contracts/v1/mail/emails/*]
        methods: [GET]
      mail.draft.send.v1:
        uris: [/contracts/v1/mail/drafts/*/send]
        methods: [POST]
        risk: high # a per-user cap on this route
```

## Applications

Each section lists the contracts proposed for one application, from its source code at the version deployed on dev. Risk applies to writes: `low` is covered by the write consent, `high` is confirmed call by call. Priority: `existing` is implemented; `P0` is the first wave; `P1` is next; `P2` waits for a product decision or a change upstream. Each section numbers its own sources.

### Calendar (Twake Agenda)

Twake Agenda keeps the owner's calendars, events, address books and contacts in esn-sabre, a CalDAV and CardDAV server backed by MongoDB. The side service, a Java service built on Apache James, stands in front of it: it authenticates users, proxies DAV, keeps users, settings and booking links in its own MongoDB database, indexes events in OpenSearch and reads the contact autocomplete index that Twake Mail writes [17]. Versions read, as deployed on dev on 2026-10-06 [1] [2] [3]: side service 2.4.6.2 ([linagora/twake-calendar-side-service](https://github.com/linagora/twake-calendar-side-service/tree/319c0f9438915a37f8f1ee77e4ec17dbd435426f) at `319c0f9`), esn-sabre 2.4.6 ([linagora/esn-sabre](https://github.com/linagora/esn-sabre/tree/7bff8ea49be33e565826f103392017014667c518) at `7bff8ea`, with [sabre/dav 4.7.1](https://github.com/sabre-io/dav/tree/f36f002dce082e1d425c4a0dc8c71a6b176c3b07) and Linagora's [fork of sabre/vobject](https://github.com/linagora/sabre-vobject/tree/d12a1f08c001de610ba91460349ca27dce92a630)), web app 1.3.1 ([linagora/twake-calendar-frontend](https://github.com/linagora/twake-calendar-frontend/tree/b8a59b9ab8ed6e8cff89aba16875b36d35315587) at `b8a59b9`), chart `twake-calendar-side-service` 1.1.2.

#### API surfaces

| Surface                          | Protocol                                                                                                | Serves                                                                                             |
| -------------------------------- | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Side service REST API            | HTTP/JSON: part of the OpenPaaS API, plus Twake routes [4]                                              | profile and settings; people, contact and event search; booking links; video links                 |
| Side service DAV proxy, `/dav/*` | CalDAV [56], CalDAV scheduling [57], CardDAV [60], and esn-sabre's JSON API in jCal [61] and jCard [62] | calendars, events, free/busy, invitations, address books, forwarded to esn-sabre as the caller [5] |
| WebSocket                        | `POST /ws/ticket`, then `GET /ws?ticket=` [15]                                                          | live updates for the web app                                                                       |

| AMQP (RabbitMQ)                  | esn-sabre publishes, the side service consumes [14]                                                     | scheduling: delivery of internal invitations, notification mails                                   |

On dev, the REST API, the DAV proxy and the WebSocket share the side service's public endpoint, `https://calendar-backend.dev.twake.lin-saas.com` [2]. Contracts call the side service from inside the cluster. The DAV proxy authenticates the caller, strips `/dav`, replays the request on esn-sabre as that user and returns esn-sabre's answer as is. It forwards a fixed set of request headers, which leaves out `If-Match`, `If-None-Match` and `If-Schedule-Tag-Match` [5]. esn-sabre's JSON API answers only when `Accept` is `application/json`, `application/calendar+json` or `application/vcard+json` [20].

#### Acting as the owner

- **Accepted as is.** The side service, the only service contracts call, accepts the broker's access token on its REST routes and its DAV proxy. esn-sabre itself does not accept it [19], so contracts reach it only through the proxy.
- **Validation.** The side service marks the JWTs it issues itself with a claim that the broker's token lacks, so its OIDC strategy handles the token [6, l. 69-71]. That strategy calls LemonLDAP's userinfo and introspection endpoints in parallel [7, l. 89-104]. The user is the `email` claim of userinfo, created in Agenda on first sight [7, l. 98-101, 126-142]. The token passes if it has not expired and one of its introspected audiences is in the side service's list, `tcalendar` on dev [6, l. 74-85] [8] [2].
- **Pilot.** Nothing to add: `twake-space-agents` already carries the additional audience `tcalendar`, and the broker's scope is enough, since userinfo returns `email`. The contracts service checks the token first (`at+JWT`, RS256, issuer, audience, `client_id` `twake-space-agents`), then relays it as `Authorization: Bearer` [52] [53, l. 100-125].
- **Reach and target.** The side service grants the token what the owner may do in Agenda and Contacts, as for a web session: contracts are what narrow an assistant to one operation per tool, and the token goes only from APISIX to the contracts service, then to the side service [51, l. 17]. The production target is a Calendar-only token from its own client, `twake-space-agents-calendar` (see [Tokens per application](#tokens-per-application)). A client of its own would also let the side service recognise assistant tokens and limit them to the routes contracts use, which needs an upstream change.
- **The owner's ids.** The contracts service knows only the token's subject, the owner's email in lower case [52, l. 132]. Today it calls `GET /api/users?email=` and keeps `[0]._id` [53, l. 139-148]. Recommended: `GET /api/user`. It takes no parameter and returns the token's user: `_id`, `preferredEmail` (the ORGANIZER address) and `configurations`, with the time zone (`core.datetime.timeZone`), business hours (`core.businessHours`) and language [9] [4, l. 70-226]. The web app starts with the same call [38]. From `_id` follow the calendar home `/calendars/<_id>`, the default calendar `/calendars/<_id>/<_id>`, and the address books `/addressbooks/<_id>/contacts` and `/addressbooks/<_id>/collected` [9] [24]. Another person's id, for free/busy, still needs `GET /api/users?email=`, which finds only users of the owner's domain [9] [4, l. 228-258].

Notes on contracts:

- **Every contract** calls the side service with the owner's token. New contracts take the owner's id, address and time zone from `GET /api/user`. Something the owner cannot see answers 404. Errors are typed problems [65]: `event_not_found`, `calendar_not_found`, `calendar_read_only`, `not_organizer`, `event_has_attendees`, `recurring_event`, `invitation_cancelled`, `not_an_attendee`, `person_not_found`, `too_many_people`, `invalid_request`.
- **Consent.** Existing pilot users keep Calendar read and write without a prompt; new users get the first-use consent. `events.read.v1` reads the assistant's feed of workplace events, not Agenda [51, l. 21-32, 85], and its `events` domain is granted for reading.
- **Risk.** Accepting, declining, tentatively accepting and `respond_to_calendar_event` are the owner's own answer: low, even though Agenda tells the organizer. Personal events without attendees are low. Every contract that mails attendees is high. So are `propose_new_time`, a proposal to the organizer with a comment the assistant may write, and `book_room`, a request to the room's administrators. `delete_event` and `delete_event_occurrence` are high because a DAV deletion is permanent. `update_event_occurrence` is high because it also serves meetings.
- **Owned calendars.** In v1, event reads, search and writes stay on the calendars the owner owns. Delegated calendars and subscriptions show only in `list_calendars`.
- **Text from others.** An event comes back with its uid, `recurrence_id`, times, title, location, status, organizer, attendees with their answers, `my_partstat` and video link. Titles, descriptions, locations, comments and names are written by the organizer, who can be any colleague, and an internal invitation lands in the owner's calendar without any action from them [14]. Contracts return that text as plain text in `untrusted`, the description truncated (the web app writes HTML [50]), with `organizer` and `organized_by_user` computed by the contract. A contract never takes an attendee address, a link or a slot from an event's text unless the owner said it, and a turn that such an invitation started writes only after the owner's yes.
- **Time.** Inputs are RFC 3339 with an offset. Outputs use the owner's time zone, and the event's own `TZID` when esn-sabre returns it: a single event keeps it, an expanded list loses it. esn-sabre reads `match` bounds as UTC and returns expanded occurrences in UTC without their VTIMEZONE [37] [22], so the contract converts both ways; the web app 1.3.1 does otherwise and is not a model here [50]. Writes carry an IANA `TZID` (from the profile, `Europe/Paris` by default on dev [2]) and a VTIMEZONE, as the web app does [41]. All-day events use `VALUE=DATE`.
- **Writes.** The proxy drops preconditions (see Open points) and a jCal `PUT` returns no ETag [36]. Contracts therefore choose the UID and read with `REPORT {"uid"}` just before writing and again after a failure, so that a retry neither creates twice nor mails attendees twice. The side service waits up to 120 s for esn-sabre [3] and the contracts service gives up after 10 s [55], so a write can land after a timeout.
- **Recurrence.** P0 writes refuse recurring events (409 `recurring_event`); a stored invitation does not say which occurrence it is about [51]. Lists return each occurrence with its `recurrence_id`. An answer on the whole series overrides the owner's later answers on single occurrences [28], hence the explicit choice in `respond_to_calendar_event`.
- **Deleting with attendees.** An organizer's DELETE cancels the meeting for everyone, and an attendee's DELETE declines the whole series [25] [37]. That is why `delete_event` refuses events with attendees.
- **Meetings.** esn-sabre schedules only when the ORGANIZER is the account's first address: with an alias, no invitation leaves and nothing says so [26]. Contracts use `preferredEmail` and compare addresses in lower case; aliases are not recognised, as in `events.read.v1` [51]. External attendees get iMIP mails from the side service [59] [14]. Past events send no notification [14].
- **Availability.** Other people's free/busy is reduced to free, busy or unknown, or to common slots: contracts never return other users' event identifiers or busy ranges. Ids come from `GET /api/users?email=`, because an unknown or foreign id fails the whole free/busy call [32]. Business hours default to 8:00-19:00, Monday to Friday, on dev [2]. A declined event does not count as busy [29].
- **Bounds.** The range `REPORT` has neither pagination nor cap [22]: the contract bounds the window and the calendars, cuts at `limit` and sets `truncated`. Event search reports the page size as its total [10]. People search stops at 256 results [11]; contact search applies `offset` and `limit` after merging the books [12]. A list costs 1 + N `REPORT`s and an availability check one lookup per person plus one free/busy call, so both are bounded.

#### Kept out

- **Sharing a calendar, delegating, answering a delegation** (`{"share":…}`, `{"invite-reply":…}`): gives a third party the owner's data, and is a classic injection target [39] [21].
- **Making a calendar public, subscribing to another person's calendar** (`ACL` with `public_right`, `calendarserver:source`): publishes to the whole domain, or reads someone else's calendar [39] [21].
- **Listing another user's calendars, rights or sharees**: exposes a third party's calendar names, descriptions and sharees [21] [20].
- **Secret links** (`…/secret-link`, `calendar.ics?token=`): a bearer URL that serves the calendar without authentication [4, l. 399-421].
- **OpenPaaS JWTs** (`POST /api/jwt/generate`): a second bearer credential for the owner, outside the contracts [4, l. 564-576].
- **WebSocket tickets** (`POST /ws/ticket`): a ticket is a bearer credential, and live updates serve no contract [15].
- **Import and export** (`POST /api/import`, `?import`, `?export`): bulk writes or reads, outside scheduling [4, l. 723-783].
- **Creating, renaming or deleting a calendar; moving an event**: deleting a calendar erases all its events, and none of it serves an assistant in v1 [39] [40].
- **Settings** (`PUT` or `PATCH /api/configurations`): time zone, language, alarm mails; a `PUT` replaces the whole object [4, l. 355-396].
- **Booking links**, other than listing them: creating, changing or deleting one publishes the owner's availability on a public page, and booking on someone else's creates events for them [15].
- **Participation links received by mail** (`…/participation?jwt=`): they act on a plain GET; an assistant never follows a link read in a mail or an event [4, l. 704-721].
- **Generic DAV access**, any `/dav/*` request a contract does not build itself, iTIP posts included: contrary to one operation per tool [5].
- **Administration** (webadmin, administrator accounts, resources, team calendars): acts for any user of any domain [15].
- **Deleting, moving or copying contacts; sharing or publishing an address book**: data loss or exposure, with no value for an assistant [34].
- **Acting in a calendar someone delegated to the owner** (v1): it commits a person who has not consented to an assistant; a product decision [39] [20].

#### Open points

- **Product decision: exposing colleagues' availability to an assistant.** Agenda lets any user of the domain read another user's free/busy, and the web app shows it when inviting [36] [47]. Until it is decided, `check_people_availability` and `find_meeting_slots` return only free/busy flags or common slots.
- **Product decision: delegated calendars and subscriptions.** Reading them, then acting in them, is left out of v1.
- **Product decision: rooms.** They are hidden on dev, and every booking waits for an administrator [2] [14].
- **Upstream: conditional writes.** The DAV proxy drops `If-Match`, `If-None-Match` and `If-Schedule-Tag-Match`, in 2.4.6.2 and on `main` on 2026-10-06 [5] [18]. esn-sabre honours them [36], and the side service uses them for its own writes [16]. Forwarding them is a three-line change; RFC 6638 recommends `If-Schedule-Tag-Match` for scheduled objects [57].
- **Upstream: video links.** They wait for Meet to be wired to the side service: `POST /api/videoconference` answers 404 on dev [13] [2]. The link the web app builds depends on a `workplaceFqdn` claim that the contracts service does not have [49].
- **Upstream: COUNTER has no follow-up.** The organizer gets a mail, but neither the web app nor the side service lets them accept or decline the proposal, and DECLINECOUNTER is not implemented [14] [37] [58].
- **Recurrence.** Acting on one occurrence needs the web app's handling of `RECURRENCE-ID`, exceptions and `EXDATE` [43] [46]. A series of more than 3,500 occurrences from its `DTSTART`, such as a daily series longer than about nine years, silently disappears from reads and free/busy, `read_freebusy` included [37] [35].
- **Reads with side effects.** The first call with a token creates the owner in Agenda, and `GET /api/users?email=` creates the person looked up when the directory has them [7] [9].
- **Introspection.** The side service rejects every token when LemonLDAP's introspection lacks `aud`, a field RFC 7662 leaves optional [7, l. 115-124] [64]. LemonLDAP upgrades must keep it (see [Tokens per application](#tokens-per-application)).

### Mail (Twake Mail)

TMail, the Twake Mail backend, holds the owner's mail. Cassandra keeps mailboxes, message metadata and keywords, labels, filter rules, identities, the vacation response and settings. S3-compatible object storage keeps message content and attachments, plus a deleted-messages vault (one year by chart default). OpenSearch keeps the full-text index, which includes the text of attachments. Redis caches validated tokens and rate-limit counters, RabbitMQ holds mail in transit, and users come from LDAP, read-only [2] [3]. The web client (chart `linagora/tmail-frontend` 1.0.12) holds no objects [1]. Versions read, as deployed on dev on 2026-10-06: image `linagora/tmail-backend:distributed-ai-1.0.20` from chart `linagora/tmail-backend` 5.4.63 [1] [2] [3]; its source, linagora/tmail-backend at tag `1.0.20` (commit `5c6a705`), whose release notes name this image for deployments with AI features (the image has no revision label, so the match rests on these notes and on dates) [4]; and Apache James at commit `20bf808`, the submodule that tag pins [4].

#### Acting as the owner

TMail does not accept the broker's token as is. That token's `aud` is `twake-space-agents` and `tcalendar` (see the tokens section), and TMail on dev accepts `twakemail` and `teammail-mobile` [2].

- Dev enables two JMAP authentication strategies, OIDC then ticket, tried in order [3] [8]. TMail 1.0.20 runs the Apache James OIDC code [4] [7].
- For a bearer token, TMail first looks in a 5-minute Redis cache keyed by a SHA-512 hash of the token. On a miss, it calls LemonLDAP's introspection with its own client credentials and userinfo with the token, in parallel [8].
- The deployed LemonLDAP portal (`yadd/lemonldap-ng-portal:lts-2.21-hiperf`, built from guimard/llng-docker `v2.21.6-1`) adds `aud`, `iat`, `nbf` and `token_type` to the introspection answer [14]. TMail requires one of its configured audiences in `aud`, then checks `exp`. The user is the userinfo `email` claim, and the session opens without delegation [8].
- Pilot: add `twakemail` to the additional audiences of the LemonLDAP client `twake-space-agents`. Userinfo must return `email` for that client, as plain JSON (TMail parses userinfo as JSON [8]), equal to the TMail username.
- JMAP has no scopes: a token TMail accepts opens the owner's whole mailbox. The contracts service narrows it to the operations below and never logs it.
- Production target: a per-app token whose only extra audience is `twakemail`, held by the broker.
- Account: the contracts service calls `GET /jmap/session` with the token [15 §2]. It checks that `username` equals the token's `sub`, lowercased (otherwise `mail_account_mismatch`), and takes `accountId = primaryAccounts["urn:ietf:params:jmap:mail"]`, always the personal account. Accounts delegated to the owner also appear in `accounts`, with `isPersonal: false`, and are ignored [9]. The id is also the SHA-256 hex of the username, a cross-check only [9]. The result is cached per token hash for 5 minutes at most. The session's absolute URLs carry the public prefix: the service keeps its internal base URL [9] [3].

**Notes on contracts**

- Every operation calls `POST /jmap` with the owner's token and a `using` list limited to what it needs. None uses `urn:apache:james:params:jmap:mail:shares`: without it, James returns only personal mailboxes and searches only the personal namespace [10]. A message outside personal mailboxes, which each contract checks itself, answers 404, like an unknown one, and lists leave it out [20].
- Mailbox roles (`inbox`, `drafts`, `sent`, `trash`, `archive`, `spam`, `templates`, `outbox`) come from `Mailbox/get`, read anew by each call. James derives them from the default mailbox names [11]. TMail leaves out the properties a mailbox lacks, the role of an ordinary mailbox and the parent of a top-level one, which `list_mailboxes` gives as `null` [20].
- Common bounds: `limit` 1 to 100 (default 20); one message per write, no batch. Reading never marks a message as read: only `mark_email` changes `$seen`.
- Never returned to the model: the token, raw headers and MIME, download URLs, attachment binaries.
- Errors are RFC 9457 problems with a type [18]: `email_not_found`, `thread_not_found`, `mailbox_not_found`, `attachment_not_found`, `attachment_unsupported`, `attachment_too_large`, `label_not_found`, `draft_not_found`, `not_a_draft`, `draft_changed`, `forbidden_sender`, `too_many_recipients`, `mailbox_forbidden`, `mailbox_ambiguous`, `trash_ambiguous`, `email_in_spam`, `invitation_not_found`, `mail_account_mismatch`, `mail_refused` (TMail answered 401), `mail_unavailable`, `invalid_request`.
- `list_emails` and `search_emails`: James rejects `inMailbox` and `inMailboxOtherThan` nested in filter operators, so each query uses one `FilterCondition`; James also gives no reliable total [10]. The cursor is opaque. `text` matches addresses, subject, body, and attachment names and extracted text [10].
- `list_emails` takes no `label` yet: a label filter comes with `list_labels`, and takes a label id, never a raw keyword. With TMail's `needs-action` label, it lists what TMail's LLM classifier marks as needing action: a hint, not a fact [7].
- `read_attachment` accepts `text/plain`, `text/csv`, `text/markdown` and `text/calendar`. PDF and Office files would go through Tika later (P2), once its parser surface is reviewed.
- `read_email_invitation` is the bridge to Calendar: its `uid` finds the invitation there, and the Calendar contract answers it.
- Drafts are low: nothing leaves the mailbox, and the owner reviews and sends them from Twake Mail or through `send_draft`. A reply draft goes to Reply-To, else From, and with `reply_all` to the other recipients as well, never to the owner. It takes the original for one the owner wrote only when it is in their Sent mailbox and its From is one of their addresses, and then answers those it went to; any other message is answered as one received, whatever its From says. The answer names the recipients under `untrusted`, and `reply_to_differs` flags a Reply-To that differs from From [20].
- `send_draft` is high: it sends a text the assistant wrote. JMAP email content is immutable [16 §4.1], so the approval binds `draft_id` and a digest of recipients, subject and body; the contract checks the draft is still in Drafts, with `$draft`, unchanged. James stores no submission and cannot cancel one; the contract never sets `holdFor` or an envelope [10]. TMail refuses a `From` the owner may not use (`forbidden_sender`) [10]. A reply then gets `$answered` on the original. Bounces come back as messages in the inbox. The contract keeps a per-owner send quota on top of the APISIX cap.
- `move_email`, `archive_email` and `trash_email` are low: the message can be moved back. Each patches `mailboxIds`, the target in and the owner's other mailboxes out, so that a mailbox shared with the owner keeps the message [20]. It stays in Trash unless the owner turned on TMail's Trash cleanup (off by default, weekly or monthly) [5]. A deleted message can then be restored for 15 days [6].
- `report_spam` and `report_not_spam` are high: each reports a message to TMail's spam filter. In James, a `mailboxIds` change is a move [10] [11], and TMail reports a move into Spam as spam, and a move out of Spam (not to Trash) as not spam [12].
- For the same reason, `move_email` and `archive_email` refuse a message that is in Spam (`email_in_spam`): taking it out of Spam is `report_not_spam`'s work. `trash_email` still takes it out, since a move to Trash reports nothing [12]. `move_email` also refuses Spam as a target, which is `report_spam`'s work, as well as Drafts, Sent, Outbox, Templates and Trash (`mailbox_forbidden`). A name or a role that several of the owner's mailboxes share is refused rather than guessed: `mailbox_ambiguous`, or `trash_ambiguous` for several trash mailboxes, among which no contract chooses [20].
- `set_vacation_response` is high: TMail sends its text to each sender once for the period, except automatic mail and `-noreply` senders, at the Reply-To address [13]. `x-twake-risk` is set per operation, so `clear_vacation_response` stays low in the same contract.
- `create_filter_rule` is high: the rule acts on every future message until the owner deletes it, and its effects are hard to undo. `Filter/set` replaces the whole rule list, so the contract reads the rules, appends one and writes with `ifInState` [5]. Filter rules created by the assistant never forward, reject, create a mailbox by name, or move to Trash or Spam.
- `reply_email_invitation` is low, like the Calendar answers to an invitation: the reply is the owner's own answer, not a text the assistant wrote. On dev TMail runs without a calendar server: it queues an iMIP reply and flags the message, and Twake Calendar is not updated [2] [7]. For an invitation Calendar knows, the Calendar contract answers; this tool is for external organizers (product decision pending).
- `restore_deleted_emails` restores into `Restored-Messages`, at most 5 messages per action, deleted within the last 15 days [5] [6].

#### Kept out

- `Email/set destroy`, `Mailbox/set destroy`, `Mailbox/clear`: permanent once the 15-day restore window ends [6].
- `Mailbox/set update` (rename or move a mailbox): low value, and it can disorganize the mailbox.
- `Forward/set` (disabled on dev) and the filter actions `forwardTo` and `reject`: they send mail away or drop it, silently, for every future message.
- `FolderFilteringAction/set`: replays the filters over a whole mailbox at once.
- `Identity/set`: changes the Reply-To or signature of every message the owner sends.
- `Delegate/set`, `DelegatedAccount/set` and sharing rights: they give another account access to the mailbox.
- `TeamMailboxMember/set`, `TeamMailbox/revokeAccess`: team administration.
- `PushSubscription/set`, Firebase registration, WebPush: they send mailbox events to an outside endpoint.
- `UnauthenticatedBlobAccess/set`, `PublicAsset/set`: they create links that work without authentication, or publish content.
- `POST /upload-from-url`: it makes the server fetch a URL.
- `GET /downloadAll` and raw message download: bulk export, and raw headers carry routing data (`Received`, IP addresses).
- `MDN/send`: it tells the sender the message was read.
- `Email/import`, `Email/parse` of raw data, `Blob/copy`: they can fabricate a message in the mailbox or copy data between accounts.
- `POST /upload` of model-written content: not needed while the assistant attaches nothing new.
- `EmailSubmission/set` outside `send_draft`: no envelope override, no delayed send (it cannot be cancelled), no sending of a non-draft.
- `AiBot/Suggest`, `/ai/v1/chat/completions`, `Settings/set`: a second LLM would process the owner's mail, and settings change the owner's preferences and AI switches.
- Disabled or not applicable on dev: `Email/send`, `Keystore/*` and `EncryptedEmail*/get` (pgp disabled), `CalendarEventCounter/accept` (no counter support without a calendar server).
- Push channels, IMAP, SMTP, POP3, ManageSieve, WebAdmin, and direct access to the storage backends.
- Other people's mail: shared mailboxes, team mailboxes and delegated accounts. Including them is a product decision.

#### Open points

- Blocking for the first contract: after `twakemail` is added, call `GET /jmap/session` with a broker token on a test account. Expect 200 and `username` equal to the owner's email. This also checks that userinfo returns `email`, unsigned, for `twake-space-agents`.
- Prompt injection is the main risk of this app. The harness passes the whole contract response to the model [19], so the contract sorts what it returns. Design rules:
  - Everything a third party writes goes in an `untrusted` object, apart from trusted metadata (ids, dates, mailbox, flags): names and addresses, subject, preview, body, Reply-To, attachment names and text, calendar fields, collected contact names, auto-replies, bounces, and the `needs-action` label, which an LLM sets from the message itself.
  - Untrusted text loses what a reader does not see, every control character but whitespace and every format character, invisible or bidirectional (Unicode's Cc, Cf and Cs), and is capped in size: 1,000 characters for a subject or a preview, 200 for a name, 320 for an address, 100 addresses per header [20].
  - HTML to text: the contract asks the server for text values (`fetchTextBodyValues`), then collapses whitespace, caps the text, and reports TMail's `isEncodingProblem` as `body_unreadable`. It never assumes the text matches what a person sees in the message [10].
  - A Reply-To that differs from From is flagged by `read_email`, and by the answer of a reply draft, which names the resolved recipients.
  - External senders and recipients are flagged. Spam and Trash are left out of lists and search unless the owner names them.
  - Turns triggered by an event get metadata only, no bodies.
  - The frozen call shows what the contract resolved (recipients, Reply-To, exact text), not the model's paraphrase.
  - One message per write, per-owner quotas on writes, and calls serialized per owner.
  - Mail content never goes to the assistant's long-term memory, and Mail tools are offered only in the owner's private conversation.
- Security emails (one-time codes, password-reset or sign-in links): mask or exclude them; the rule is to be decided.
- Marker on drafts written by the assistant: a keyword (private) or a header (visible to recipients). Product decision.
- Attribution: TMail records the owner as the author of every action; only the gateway audit names the assistant [10].
- Revocation: TMail caches a validated token for 5 minutes, so a withdrawn consent takes effect within that delay, unless TMail receives a back-channel logout for the session [8].
- No delivery status: there is no `EmailSubmission/get`, and bounces arrive in the inbox [10].
- To check live: thread grouping on dev; whether the rspamd status headers are stored with each message (a spam score as a trust hint); the label name of `needs-action` in `Label/get`; the session's actual capabilities; `calculateTotal` support.
- Product decisions: `send_draft` quotas; team mailboxes; replies to external invitations through TMail; the risk class of the spam reports, to revisit.

### Drive (Twake Drive)

Twake Drive is the Cozy web app `drive`. The user's objects live in cozy-stack, not in the app: file and note metadata, sharings and permissions in CouchDB, file contents on local disk, Swift or S3 [1][2]. The admin panel installs Drive from `registry://drive/stable` [3]; on 2026-10-06 that channel served version 1.107.0, published on 2026-09-08 [4]. This section reads linagora/twake-drive at tag 1.107.0 [5] and cozy-stack at release 1.6.63 of 2026-09-30, its latest release [6]. cozy-stack is hosted outside the deployment repository: instances are created on the Cloudery that Cozy hosts, and the Cozy cluster serves them [7]. The stack version running on dev cannot be read from the repository.

#### API surfaces

| Surface                                            | Protocol                                | Serves                                                                |
| -------------------------------------------------- | --------------------------------------- | --------------------------------------------------------------------- |
| Stack REST API, `https://<instance>/`              | HTTPS, JSON:API, cursor pagination [8]  | Files and folders, notes, sharings and shared drives, links, settings |
| Stack authorization, same host                     | HTTPS, OAuth 2.0 and token exchange [9] | Client registration, consent, tokens                                  |
| Realtime, `wss://<instance>/realtime/`             | WebSocket [10]                          | Document events for a holder of a Cozy token; not used                |
| AI relay, `https://<instance>/ai/v1/tools/execute` | HTTPS multipart [11]                    | openRAG tools such as `extractText`, when a RAG server is configured  |
| Drive web app, `https://<name>-drive.<domain>/`    | HTTPS, hash routes [5]                  | Links for the owner; not an API                                       |

`<instance>` is the owner's instance host, `<name>.<domain>`. With flat subdomains, the stack serves each app on `<name>-<app>.<domain>` [12]. The API path carries no version: it follows the stack release.

#### Acting as the owner

- **Token check.** cozy-stack accepts only a bearer JWT signed with HMAC under an instance secret chosen by its single audience, and issued by the instance's own domain [13][14][12]. The broker's LemonLDAP token is an RS256 JWT [15]: it fails, so the contracts service needs a Cozy token.
- **First wave: OAuth consent on the instance.** A client for the assistants is registered on the owner's instance. The owner approves the stack's consent screen once (authorization code with PKCE; scope `io.cozy.files:GET,POST` for P0, plus `PATCH` for P1, never `*`), then tokens are issued and refreshed at `POST /auth/access_token` [9][16]. One instance, the consented scope only, a client the owner can list and revoke [17], no platform change.
- **Target: `POST /auth/token_exchange` with `exchange_type: app`.** The stack trades the owner's LemonLDAP token for a Cozy token without a second consent, after checking the signature against the provider's keys, the issuer, `iat`, `exp`, `sid`, an audience listed in `app_token_exchange`, and an instance claim equal to its domain [9][18][19]. It needs cozy-stack 1.6.57 or later [20], the context configured by the Cozy operators, `sid` and the instance claim in the LemonLDAP token, and a narrower scope: the exchange grants a linked app's whole manifest and rejects a requested scope [19], while Drive's manifest goes well beyond files [5], hence an upstream change or a dedicated linked app limited to `io.cozy.files`. In 1.6.63 each exchange creates an OAuth client, within 50 per hour per instance [19][21]: the service caches the client and its refresh token.
- **Rejected paths.**
  - `POST /oidc/access_token`: it does not check the audience of the token it receives.
  - `exchange_type: admin`: reserved to organization administrators [9].
  - Stack administration and Cloudery partner credentials: the owner never consents to them.
- **Finding the instance.** Its host is assigned when the account's instance is created, and kept in the directory [22]: it is read from the owner's `workplaceFqdn` claim in LemonLDAP-NG (as in cozy-stack's examples [18]), never derived from the email. The Cozy token reaches only the owner's own instance, and the contracts service never stores it: when no instance of the platform is known for the owner, the contract answers `drive_instance_unknown`, and without a Cozy token, `missing_drive_token` [36]. A wrong host fails closed: the exchange compares the claim with the instance domain, and the first-wave consent is given on the instance itself.

**Notes on contracts**

- **Risk and consent.** `low` writes are covered by the owner's write consent for Drive. `high` writes (`share_file`, `create_public_link`) are shown to the owner as a frozen call and run only after an explicit yes, one call at a time; APISIX also caps them per user. A turn triggered by an event never runs a Drive write directly: the harness asks the owner with context, then resumes after the yes.
- **Writes stay outside sharings.** Sharing rules propagate new and changed documents to the other members [29]. So `create_file`, `create_note`, `create_folder`, `move_file` (destination), `restore_file` (restore path) and `restore_file_version` refuse a target inside a sharing or a shared drive: putting content there shares it, which is `high` and goes through `share_file`. `create_file` also refuses a folder that a link shares, until the link expires, since its holders read what the folder holds, and answers `409 folder_shared` [36].
- **Calls and errors.** Calls go to the instance host with the Cozy token. A stack `403` or `404` becomes a typed `404`; `412` becomes `concurrent_change`, `401` `drive_refused`, a `5xx` or a timeout `drive_unavailable`. Each change to an existing item reads its revision first, then writes with `If-Match` [1]. `limit` runs from 1 to 100 (20 by default); `cursor` is opaque, 1,024 characters at most.
- **One route per contract.** Each contract has its own pair of path prefix and methods, so APISIX keeps one route per contract.
- **Fields.** Responses keep an allowlist: `id`, `type`, `folder_id`, `size`, `created_at`, `updated_at` and `web_url`, with the `name`, `path`, `mime` and `class` under `untrusted`: people wrote the names, and the type is the one the uploader declared, from which the stack derives the class [36]. Never returned: Cozy tokens and client secrets; link codes, except the link that `create_public_link` was approved to create; thumbnail and download secrets (`links`, valid 10 minutes [1]); `metadata` (EXIF, including location, and document qualification); `cozyMetadata.sourceAccount*`; `md5sum`; client-side encrypted content. Sharing members: name, email and status only.
- **Untrusted content.** Names, file contents and notes written by others reach the model: shared files and drives, uploads through links, saved mail attachments, connector imports, collaborative notes. They come back under `untrusted`, the type and class of a file included, size-capped, without control characters but the tabs and line breaks of a text [36].
- **Links for the owner.** `web_url` (`#/folder/<dir_id>/file/<file_id>`, or `#/folder/<id>` for a folder) opens the Drive app in the owner's own session [5], on `<name>-drive.<domain>` when the stack serves its apps on flat subdomains, else on `drive.<instance>`. The service builds it from the instance host and the stack's `flat_subdomains` capability [17][36], never from `/office/:id/open` or `/editor/:id/open`; no `office_url` (`#/onlyoffice/<file_id>`) is offered yet.
- **Sizes and paging.** The stack does not cap downloads, so the service does (`max_bytes`). A note import is capped at 2 MiB [25]; a full instance answers `413` [1]. Folder contents and the trash page by 30 by default, `_find` by 100 [1][23]. The service pages a folder with `page[skip]`, from its first page, so that no cursor it returns carries an item's name, which belongs under `untrusted` only [36]. The sharing and shared drive lists are not paginated: the service truncates them and says so.
- **Search cost.** With no CouchDB index on `name` [24], `search_files` scans the owner's files; the service bounds its time and limit. The first `list_recent_files` call creates its index, so it is slow.
- **Rates.** The stack limits only some actions per instance: OAuth client creation, sharing invitations, public link views [21]. Beyond them, APISIX limits the harness as a whole, and the harness's own admission limits each owner [30].
- **Trash.** An item in the trash can be restored until the stack empties the trash [1].

#### Kept out

- Permanent deletion: `DELETE /files/trash/:file-id`, `DELETE /files/trash`, `permanent_delete` in `PATCH /files/:file-id`, and version deletion (`DELETE /files/:file-id/:version-id`, `DELETE /files/versions`). It cannot be undone [1].
- Writable links, link edits and revocations (`PATCH` and `DELETE /permissions/:id`), and link permissions on shared drives [16][28]. v1 creates read-only links only, each after the owner's yes; the owner manages links in Drive.
- Routes that mint secret URLs usable without authentication: `GET /office/:id/open`, `GET /editor/:id/open`, `GET /notes/:id/open`, `POST /sharings/:id/preview-url`, `POST /files/downloads`, `POST /files/archive`, and their shared drive versions [1][25][31][26][28]. The owner gets a Drive app URL instead.
- Overwriting content: `PUT /files/:file-id`, `PATCH /notes/:id`, `POST /files/:file-id/versions`, and any edit of a file someone else created or shared [1][25]. A mistake would overwrite the owner's work, or a third party's through synchronization; v1 only adds new files.
- Sharing management beyond `share_file`: removing or adding members, creating shared drives (`POST /sharings/drives`), moving between drives (`POST /sharings/drives/move`), writing inside a shared drive [27][28].
- Generic access: `/data/:doctype/*`, `POST /files/_find` or `_all_docs` with a selector from the agent, `GET /files/_changes`, the `/realtime/` websocket. The agent never supplies a doctype or a Mango selector.
- The other doctypes of Drive's manifest: `io.cozy.accounts`, `io.cozy.jobs`, `io.cozy.triggers`, `io.cozy.ai.chat.*`, `io.cozy.oauth.clients`, settings beyond disk usage, Nextcloud migrations [5]. Files do not need them.
- Platform credentials: the stack administration API, Cloudery partner tokens, service secrets. The owner never consents to them.
- Administration and maintenance: `fsck`, RAG administration, import and export, `POST /files/upload/metadata`.

#### Open points

- **Who holds the Cozy token.** The first wave adds a consent step on the instance and an encrypted store for the Cozy refresh token, which does not expire [32]. The contracts service never stores a Cozy token, and only reads its own database, as a read-only user [15][36].
- **Instance consent and harness levels.** Decide whether the instance consent follows the harness levels (`GET` at the first read consent, `POST` and `PATCH` at the first write consent) or asks once for the first-wave scope. Each widening needs a new consent on the instance [9]. An instance may cap its connected OAuth clients, which can block the registration [9][33].
- **Target prerequisites.** The stack version and context configuration on dev are not visible from the deployment repository: to confirm with the Cozy operators. Client reuse across exchanges exists only on master, after 1.6.63 [20].
- **LemonLDAP.** Release `workplaceFqdn` for the assistants' client; put `sid` in the token presented for the exchange. Exchanged clients are bound to that `sid` and deleted by back-channel logout [9][33], so if an offline session carries the interactive SSO session's `sid`, signing out ends the Cozy client too.
- **Text extraction.** Nothing in the stack turns a PDF or an office document into text, except openRAG's `extractText` relayed by `/ai/v1/tools/execute` when a RAG server is configured (unknown on dev) [11]. The stack's RAG indexes only the assistants' knowledge folders, so there is no general full-text search [11]. Decide between extraction in the contracts service, with libraries vetted against hostile files, and openRAG.
- **Drive events.** cozy-stack publishes no file events: its RabbitMQ publishers cover account deletion and Nextcloud migration only [34]. File events stay inside the stack (realtime, `@event` triggers) [10][34], and the dispatcher wakes assistants on calendar invitations only [35]. Options: a publisher in cozy-stack, or an app service on `@event io.cozy.files`; polling `_changes` user by user is to be avoided. File ids differ between instances in a sharing [29], so an event for a recipient must carry the recipient's id.
- **Sharing scope.** `share_file` needs every verb on the file and access to contacts [27], so enabling it widens the instance scope: product decision. On cozy-stack master, sharings between members of one organization are accepted automatically [20]: a shared file would land in the recipient's Drive without their action.
- **Public links.** The stack supports an expiry (`ttl`) and a password on links [16]: decide the defaults. Revoking a link the assistant created is not offered in v1.
- **Writes near sharings.** Detect a shared target reliably (sharings sent and received, nested folders, shared drives). Decide whether writes inside a sharing come later as `high` contracts.
- **Search load.** Measure `search_files` on a large instance.

### Tasks (Twake Tasks)

Twake Tasks keeps all of a user's objects in its backend's PostgreSQL database, separated by organization with row-level security [3][4]: projects (the personal project that holds the Inbox, shared projects, and projects managed for a Twake Space), boards, sections, tasks and subtasks, labels, assignments, comments, reminders, follows, notifications and history. This version has no attachments [3]. This section reads backend 0.1.1 and frontend 0.1.0, deployed on dev on 2026-10-06 [2], from [linagora/twake-tasks](https://github.com/linagora/twake-tasks) at tag `backend-v0.1.1` (commit `adbca218`); tag `frontend-v0.1.0` (commit `c5e0435`) is its parent commit [1].

#### API surfaces

The frontend serves the web app and relays `/api/` to the backend unchanged [25]. |

Routes are not versioned and have no OpenAPI description; errors are `{"error": "<code>"}` bodies [9]. Tasks 0.1.1 has no webhook, API key, service account or MCP server [1], so the contracts call the REST API with the owner's token.

#### Acting as the owner

- **Not as is.** The broker's token comes from the LemonLDAP-NG client `twake-space-agents` (scope `openid email offline_access`, the email as `sub`) [31]. Tasks 0.1.1 refuses it: its audience lacks `twaketasks`, and its userinfo lacks claims Tasks needs.
- **Validation.** Each business route needs a bearer token [8], which Tasks introspects (RFC 7662 [32]) as its client `twaketasks-backend` while calling userinfo with it [7]. It requires an active, unexpired token whose `aud` holds its single configured audience (`twaketasks` on dev) [2][6], userinfo claims `sub`, `sid`, `uuid` and `email`, and equal `sub` values [7]; the deployed portal image adds `aud` to introspection through a patch [2][28]. Tasks then acts for `uuid` in the organization `org_id`, with roles from project membership, never from the token [7][11].
- **Pilot.** Add `twaketasks` to the additional audiences of `twake-space-agents` [29], export `uuid` and `org_id` for that client under a scope its tokens carry, and check that its userinfo returns `sid` [28]. Without `org_id`, Tasks silently treats the owner as a personal user, with no organization projects and an empty Inbox [4][7][10]. LemonLDAP-NG computes the introspection `sub` for the calling client and the userinfo `sub` for the token's client [28][29], so both clients must use the same identifier attribute. Acceptance check: `GET /api/projects` (no side effect) returns the same projects with the assistant's token as with the owner's [14].
- **Production target.** Per-app tokens: Tasks receives a token issued for it alone, with the same claims.
- **The owner's ids.** The contracts service knows only the owner's email, the token's `sub` lowercased [30]; Tasks derives the person and organization from the token, and `/api/my-tasks` and `/api/agenda` are relative to the caller [10]. When a contract needs the owner's Tasks user id ("assign to me"), it matches the email, ignoring case, against the board's `members` (`{userId, email}`); no match or several give `owner_not_member` [10][11]: every write refuses so, and `read_task` for a task with assignees [34]. There is no "who am I" route in 0.1.1 [9], and an alias of the owner's address does not match.

**Notes on contracts**

- **Waves.** P0 is the first wave, once the pilot token works; every call it needs downstream exists in 0.1.1.
- **Visibility.** Tasks answers 404 for an id that is not a UUID and for a board where the owner has no role [9][11], so an object the owner cannot see looks unknown. Contracts treat an archived or trashed task the same way.
- **Errors.** Tasks errors become RFC 9457 problems [33]: `board_not_found` and `task_not_found` (404), `forbidden_role` (403, the owner is a viewer), `board_archived` (409), `tasks_refused_token` and `tasks_unavailable` (502) [9].
- **Untrusted text.** Titles, descriptions, comments, history values and the names of labels, boards, projects and sections are written by other members (in a space project, by every member of the space). Contracts truncate them and mark them untrusted.
- **No replay.** Tasks has no idempotency key, so a contract never retries a write.
- **Risk.** Each write declares `x-twake-risk`. Ordinary task edits are `low` even though Tasks emails followers, new assignees and mentioned members about them: those emails are the app's own notifications (task key, title and a link) [22][23], not messages the assistant wrote. Each description says whom Tasks notifies [34]. `append_task_description` is `low` as well: members can edit the description back, while a comment stays.
- **High.** `add_comment` posts text the assistant wrote to the project's members; it can never be edited or deleted, and it notifies followers and mentioned members [9][23]. `delete_task` sends a task and its subtasks to the trash, purged after 30 days [15]. `transfer_task` can hand a task, with its description and comments, to the members of another project, and drops the labels and assignees the target lacks [17].
- **Words.** The owner's write consent for Tasks covers `open_boards` too, and Tasks' words for writing name it first: "open your boards, create tasks in them, and edit and complete their tasks, which emails the people who follow those tasks" [34].
- **`open_boards`.** Like opening the app, `GET /api/boards` creates the personal project and its Inbox if they are missing, and turns pending invitations for the owner's email into memberships [10][23]. A read must never act, since the harness also runs reads in turns that an event started, so listing boards is a write: `open_boards`, a `POST` without a body, `low` because it touches only the owner's own Inbox and the invitations made to them, and it notifies nobody [34]. Like any write, it waits for the owner's yes in a turn that an event started. Its answer gives each board's `role` (a viewer cannot write), the Inbox board (`inbox: true`), its project and whether that project is a Twake Space's (`space`).
- **`list_my_tasks`.** The agenda counts as the owner's both the tasks assigned to them and the unassigned tasks of their own projects outside spaces [10]; `assigned_to_me` marks the first kind. Due dates are local dates, hence the required `zone`; the contract splits `today` from `overdue`. In `search_tasks`, which holds anyone's tasks, `assigned_to_me` is `false` for a task without assignees and `null` for one with them, since Tasks does not say which assignee is the owner; `read_task` tells [34].
- **Keys.** A key such as `ABC-12` is unique within a project only [3], so writes take `board_id` and `task_id`, never a key.
- **`create_task`.** It takes no description: a field it does not take is refused [34]. Default section: none in the Inbox or on a board without sections, else the board's first `unstarted` section, else the problem `section_required`, which lists the board's sections, each with its `section_id`, its `category` and its name under `untrusted`; the reads give each task's `section_id` as well [34]. Subtasks nest four levels deep at most [12]. The owner follows the new task, and nobody is emailed [23]. If the follow-up `PATCH` fails, the answer is `task_created_partially` with the new task's `board_id`, `task_id` and key.
- **`complete_task`.** `POST …/complete` only takes tasks outside sections; a task in a section is completed by a move to a `completed` section, as the Tasks web app does on `main` [12][26]. A recurring task is completed for its due date and stays open, moved to the next one, which the answer gives as `next_due_date`, `null` for any other task; a task already completed is answered as it is, and nothing is written [34].
- **Mentions.** Tasks turns any `@email` of a project member in a comment into a mention: a notification, an email and a follow [23]. `add_comment` lets through only the addresses listed in `mentions`.

#### Kept out

- **Sharing and membership** (`POST …/invites`, `DELETE …/invites/{id}`, `GET …/sharing`, `PUT` and `DELETE …/members/{user}`) [9][14]: an invitation opens every board of a project to an address, an easy way for an injected instruction to leak data.
- **Board structure** (sections, moving a board to another project, archiving a board, default layout) [9][20]: one call changes many tasks for everyone, such as a section's new category completing or reopening all its tasks.
- **Marking notifications as read** (`POST /api/notifications/read`) [16][22]: it marks all of the owner's notifications read and cancels their pending emails, hiding information from the owner.
- **Personal view settings** (favorites, layouts, saved filters) [9]: no use to an assistant.
- **Creating labels** (`POST /api/boards/{b}/labels`) [18]: labels are the project's shared vocabulary.
- **Cancelling a task, duration and recurrence** [9][12]: their meaning needs a product decision first.
- **Replacing a description** [12][23]: the history keeps no text, so it cannot be undone; only `append_task_description` is offered.
- **Change stream and back-channel logout** [8][21]: protocol mechanisms, not actions.
- **Bulk operations**: the API has none, and no contract loops to imitate one.
- **Database and message bus**: never an interface for the assistants; contracts use the REST API only.

#### Open points

- **API maturity.** Tasks is at 0.1.x and moves fast: on 2026-10-06, `main` was already 12 commits ahead of the deployed tag, one of them adding a route [27]. Routes are not versioned, there is no OpenAPI, and errors are not RFC 9457 problems [9]. Contracts pin the Tasks version and are tested against its image at each upgrade.
- **No pagination.** The board read, `/api/my-tasks`, `/api/agenda`, comments and history are unbounded; search and notifications stop at 50, with no cursor [10][13][16][19]. Reading one task loads its whole board. Contracts truncate, but the downstream cost grows with the board.
- **No idempotency.** A replayed `create_task` makes a duplicate. Only descriptions carry a version; assignees and labels are replaced as a whole, so a concurrent change is lost [12][18].
- **Emails as side effects.** With SMTP configured, as on dev [2], every notification is emailed at once: to followers for each recorded change except their own, to new assignees, to mentioned members [22][23]. An unread notification of the same reason is not repeated. Creating, archiving and trashing email nobody; reminders email the owner only [16].
- **Events.** Tasks publishes `com.twake.tasks.task.{created,updated,moved,assigned,unassigned,completed,reopened,deleted,restored}.v1` [23][24]. `assigned` names the assignee by internal id only, while the contracts' event store finds an event's targets by email [30]. Comments, mentions and reminders have no event: the owner learns of them only through notifications (`list_notifications`). No Tasks events pipeline is deployed on dev [2]. Events whose actor is the owner must be ignored, to avoid loops.
- **Spaces.** The API gives no space id; the project of a Twake Space is known from `com.twake.tasks.space.provisioned.v1` [24] or by its name.
- **Names.** Members are known by email only, without display names [11].
- **Attribution.** Every write shows the owner as the actor, in history, events and comments [23]; only the gateway audit tells the assistant apart. Marking what the assistant wrote is a product decision.
- **Pilot settings.** The live settings of the two LemonLDAP-NG clients (claims released to `twake-space-agents`, identifier attributes) were not read for this section.
- **Product decisions.** Whether `create_board` and `delete_task` ship at all; cancellation, duration and recurrence.

### Chat (Twake Chat)

Twake Chat keeps the owner's objects on two servers. Synapse, the Matrix homeserver, holds rooms and direct chats, messages, memberships, read markers and receipts, presence, account data such as `m.direct`, and the encryption keys and their backup. ToM server holds the address book, profile visibility, a recovery-key vault, and invitations by email or SMS. #### Acting as the owner

Synapse and ToM accept neither the broker's token nor any LemonLDAP token. With MAS off, Synapse checks a request against application service tokens, then against its own access tokens, which people get by an SSO login [14][15][16]. MSC3861 is gone in 1.160, and dev offers no JWT login [17][2]. ToM accepts a Matrix token (cached, or checked with Synapse's `whoami`) or its own identity-service token, and forwards only `Authorization` to Synapse, so identity assertion does not pass through it [18][6].

- **Assistant identity** (AS `twake-harness`, in place): the assistant speaks in its own name. Reach: the assistants' rooms, nothing of the owner's [7][19].
- **Dedicated application service** asserting the owner with `?user_id=` [20][21]. Reach: every person on the server, with no expiry and no device. Recommended, behind a path allow-list.
- **JWT login** (`org.matrix.login.jwt`): a static LemonLDAP key in Synapse and a claim carrying the localpart, since `sub` is an email; each login makes a device and a session that outlives the LemonLDAP token [22]. Fallback.
- **Admin "login as a user"**: rejected: no contract uses a server administrator's credentials [10].
- **Not applicable**: replaying the SSO login needs the owner's SSO cookie, which the broker does not hold [23]; LemonLDAP's Matrix exchange only turns a Matrix token into a LemonLDAP one [24]; MAS would change Matrix sign-in for the whole platform [25].

**Recommendation.** A registration `twake-agent-contracts`, apart from the harness's: no URL (Synapse pushes nothing to it), rate limited, application service login closed (`io.element.msc4190`), and a non-exclusive namespace of people, not assistants [26]. Its AS token stays in APISIX, which adds it on an outbound route reserved to the contracts service and limited to this catalog's methods and paths: a registration cannot narrow endpoints [27]. The service sets `user_id` from the subject of the token it validated, never from a parameter [28]. The Chat contracts take this path: they reach Synapse at `CHAT_URL`, the gateway's outbound route, never hold the AS token, and call only `GET` on `/account/3pid`, `/joined_rooms`, `/sync`, a room's `m.room.name`, `m.room.topic` and `m.room.encryption` state, `/joined_members` and `/messages`, so that the route can allow those alone. The route admits the contracts service alone [54].

**Owner's Matrix id.** The harness maps `@alice:<server name>` to `alice@<mail domain>`; on dev both are `dev.twake.lin-saas.com` [19][29][4]. The service lowercases the email, requires that domain, and checks once (then caches) that `GET /account/3pid?user_id=@<local part>:<server name>` lists it. Synapse refuses an unknown user, which the contract returns as 404 `chat_account_not_found` [21]; a mismatch gives 409 `identity_ambiguous`, never a guess. The check relies on Synapse, which accepts identity assertion there although the spec leaves account management out of it [30][20]. The fallback is ToM's rule: the LDAP entry with that `mail`, then its `uid` [31].

**Notes on contracts**

- **Encrypted rooms.** Both kinds of rooms coexist, so every contract that reads or writes messages reads `m.room.encryption` on each call, and `list_rooms` and `read_room` say whether a room is encrypted. `list_messages` answers an encrypted room with 409 `room_encrypted`, whose `room` is what `read_room` gives, and the model tells the owner the room is encrypted, never that it is empty [54]. In an encrypted room a server-side contract sees metadata only: the room, its name, topic, members and encryption state (state events stay in clear), each message's sender and time, unread counts (every encrypted message counts, and mentions go undetected), read markers, invitations and departures [38][33]. It cannot send as the owner there either. Sending takes a device of the owner that shares the room key with each recipient device, and identity assertion has no device [38][21]. A device made on the server would lack the owner's cross-signing signature, and Twake Chat shares room keys only with signed devices once cross-signing is on [39][40][19]. Synapse does not refuse clear text in an encrypted room [41], so the contracts do (409 `room_encrypted`).
- **Risk.** `send_message`, `add_reaction` and `set_presence` (through `status_msg`) show other people words the assistant chose, in the owner's name. `invite_member` opens a room's history to someone, and `open_direct_chat` reaches a person who joins at once; neither can be taken back. `leave_room` cannot be undone in a private room. All of them are `high`. `mark_room_read` changes only the owner's own state: `low`.
- **Consent channel.** The harness asks for consent in the owner's room with the assistant, and hears only the owner there [37]. A write as the owner never targets a room where an assistant is a member, so the assistant can never answer in the owner's place.
- **Assistant identity.** `notify_person` writes in the assistant's name ("on behalf of …"), in an encrypted direct room that the harness opens [36]. It is not a contract, but the harness treats it as a high-risk act: the owner confirms each send, and each send is logged like a contract call. The peer joins at once, and their replies reach the assistant as untrusted text. When the owner invites the assistant into a room, the assistant's device, signed by its own identity, gets room keys from its arrival on, not the earlier history [19]. Today the harness joins such a room but takes no turn from it [37]. Using it is harness work: other members' messages are data, never instructions, and since every member reads the assistant's answers, contracts that read the owner's data do not run there.
- **Event turns.** A turn started by an event, such as a new message, never writes directly: the harness asks the owner with that context and resumes after the yes.
- **Visible to others.** `send_message`, `add_reaction`, `open_direct_chat`, `invite_member` and `set_presence` say in their description that other people will see the result.
- **What reaches the model.** Text comes from `body`, never `formatted_body`: for an attachment, its name, with `kind` saying what it is; a deleted message, with no text left, is left out [54]. Never tokens, `mxc://` URLs, recovery words or keys, ciphertext, other people's receipts or presence, or their email or phone beyond what they made visible in ToM [11]. Text written by others (bodies, room names and topics, display names) comes back in `untrusted`, with its author.
- **Sizes and errors.** An event is at most 64 KiB [42] and Synapse caps `limit` at 1,000 [43]; the contracts take 1 to 100 (20 by default, 50 for members), cut every text people wrote at 2,000 characters and cap the response. `list_messages` pages with Synapse's opaque `end` token, passed back as `before`; `list_rooms` and `list_room_members` page with a `next` of their own, passed back as `cursor` [54]. Errors: `room_not_found` (404, also for a room not joined), `room_encrypted` (409), `chat_account_not_found` (404), `identity_ambiguous` (409), `chat_rate_limited` (429, with `retry_after_ms` when Chat gives it), `chat_refused` and `chat_unavailable` (502), and `invalid_request` (400) for a `before` that `list_messages` did not give.
- **Rate limits and retries.** With `rate_limited: true`, the owner's own limits apply: `rc_message` (0.2 per second, burst 10) is shared with the owner's clients, and invites count against `rc_invites` [25]. Synapse keys an application service's transaction ids by path and service, not by user, for 30 to 60 minutes [44], so each `txnId` is unique across the service and stable across retries of one call.
- **Search and sync.** Server-side search skips encrypted rooms and covers rooms the owner left [45][46], so `filter.rooms` always lists the joined unencrypted rooms. `list_rooms` passes `set_presence=offline`, or the owner would appear online. Sliding sync needs a device [9], and the initial sync is costly, hence the strict filter, which also leaves out the presence of others [54].
- **New rooms and invitations.** A direct call to Synapse skips ToM's Twake presets [6]. Unencrypted Twake groups keep `shared` history, so an invitee reads past messages [47][48]. A person is given by email and resolved like the owner.
- **Federation.** v1 reads rooms already joined, and writes only where every member is on this server.

#### Kept out

- **ToM's recovery-key vault** (`/_twake/recoveryWords`, every method [12][49]): never routed; no contract reads or writes the owner's keys.
- **Anything that mints a session or a credential**: `/login` of every type (application service included), `/register`, `/logout*`, `/user/{id}/openid/request_token`, ToM's identity-service registration and its QR code login [50].
- **Keys and devices**: `/keys/*`, `/room_keys/*`, `/sendToDevice/*`, `/devices*`, `/delete_devices`, and the account data `m.secret_storage.*`, `m.cross_signing.*`, `m.megolm_backup.v1`. They are the owner's keys, and deleting a device signs the owner out [32]. No server-side device speaks for the owner.
- **Account and notification settings**: `/account/*` except `GET /account/3pid` and `GET /account/whoami`, push rules, pushers (they could forward the owner's notifications elsewhere), the ignore list, the profile and its ToM visibility.
- **Room moderation and settings**: kick, ban, unban, redacting others' messages, power levels, join rules, history visibility, encryption, server ACLs, upgrades, aliases, the room directory, reports. They change the security or the audience of a shared room.
- **Rewriting the owner's history**: redacting or editing their own messages. Out of v1, to reopen with an undo window.
- **Media**: files up to 200 MB, and any document can carry injected instructions [4].
- **Calls and real time**: calls (LiveKit), typing, other people's presence and receipts (privacy), raw `/sync`, sliding sync, `/initialSync` and `/events` (a generic proxy) [4].
- **Entering new rooms**: `/join`, `/knock`, public rooms and rooms on other servers. They widen exposure.
- **Administration**: `/_synapse/admin/*`, and ToM's admin and metrics routes [13].
- **ToM's outbound sends**: SMS, and invitations by email or SMS [13].
- **Address book writes**: one `DELETE /_twake/addressbook` empties the whole book [11].
- **Any call to ToM with the owner's identity**, and creating groups or channels in the owner's name (a product decision).

#### Open points

- **Prerequisite.** No contract acts as the owner before two things exist: the `twake-agent-contracts` registration (loading it restarts Synapse), and the outbound APISIX route, which admits the contracts service alone, with its allow-list and the AS token kept in the platform's secret store. The contracts settled the choice between the application service and JWT login: they take the application service, through that route [54].
- **Hardening.** To evaluate: APISIX, rather than the contracts service, sets `user_id` from the owner's token after checking its signature, issuer and audience.
- **Encryption mix.** Synapse does not encrypt new rooms by default, and ToM's proxy allows both [25][1]; the client decides. Direct chats opened from contacts, search or a profile are unencrypted [51]; those opened from recent chats are encrypted when the peer has keys [52][39]; groups are unencrypted unless their creator turns encryption on [47]; the assistants' rooms are encrypted [36]. What a contract can read thus varies by room.
- **Invites joined at once.** The deployment joins invitations on arrival [4][25]. The owner's room list can hold rooms that other people put them in, and anyone the owner invites is in the room at once. Room names and topics are therefore untrusted, and inviting is high risk.
- **Email to Matrix id.** To confirm: which LDAP attribute LemonLDAP releases as `preferred_username`, from which Synapse takes the localpart, while ToM uses the `uid` [16][31]; accounts whose email is on another login domain (`mycozy.cloud`, `twake.app`) [29]; and the directory scope, since ToM reads the LDAP's user branch only, not its B2B branch [4][53].
- **People search.** The directory behind `search_people` (LDAP or ldap-rest) is not chosen.
- **Other people's messages at the AI gateway.** What colleagues wrote goes to the external AI gateway when a contract reads it. This needs a decision from the data protection officer.
- **Visible AI marker.** Recipients cannot tell that the assistant wrote a message sent as the owner. Marking it is a product decision.
- **Encrypted direct chats.** Whether `open_direct_chat` creates encrypted rooms, which would then be closed to the contracts, is a product decision.
- **Federated rooms.** Writing where some members are on other servers is not decided.

## Risks shared by every application

- **Prompt injection.** Mail bodies, event descriptions, files, tasks and messages written by other people reach the model. The guards do not rely on the model: the harness reads consents and approvals itself, a turn started by an event cannot write, a high-risk act runs only as the frozen call the owner confirmed, contracts compute recipients and targets themselves, and text from others comes back as `untrusted`.
- **Who reads the answers.** An assistant hears only its owner: messages from anyone else in its room are ignored ([`src/matrix/role.ts`](../src/matrix/role.ts)). But every member of the room reads what it answers. Contracts that read the owner's data should run only when the owner is alone with the assistant in the room.
- **Side effects in the applications.** Some writes make the application notify people: Calendar mails attendees about a meeting and the organizer about a reply, and Tasks emails a task's followers about most changes. Each contract says so in its description.
- **What reaches the AI gateway.** Everything a read contract returns goes to the model provider. Contracts return text rather than raw MIME or binaries, cap sizes, and leave out what the owner did not ask for.
- **Unconditional writes.** Some applications cannot make a write conditional: the Calendar proxy drops `If-Match`, and Tasks has no preconditions. The last write wins, so contracts read just before they write.
- **Rate limits.** APISIX limits the harness as a whole and caps high-risk routes per user. Contracts that search or list keep their own bounds.

## Open questions

- **Budgets.** The harness's per-owner limits (tool calls per turn, tokens per day) were sized before any application contract. Reading mail or files will use them up much faster.
- **Marking what an assistant wrote.** Every application records the owner as the author of what a contract does; only the gateway audit names the assistant. Whether drafts, messages, comments and events written by an assistant carry a visible marker is one decision for all applications.
- **Other people's content at the AI gateway.** Reading mail, messages, events, tasks or files sends what colleagues and outsiders wrote to the model provider. This needs the data protection officer's view, once for every application.
- **Production tokens.** One client per application on the deployed LemonLDAP-NG, or an upgrade to 2.23.2 or later first.
- **Consent duration.** How long the broker's offline session lasts before an owner must consent again.
- **Delegated and shared data.** Delegated calendars, shared and team mailboxes, shared drives and other people's rooms are all left out of v1. They are better decided together.

Each application lists its own open points in its section.
