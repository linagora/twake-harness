# twake-harness

The Twake Space agent harness: one shared service, written in TypeScript, that gives every user of a Twake Workplace platform a personal assistant in Twake Chat, and gives the organization an analysis agent.

- Isolation between users is enforced in code and in the database, not by separate pods.
- Assistants are created by their owner from Twake Chat, through a creator conversation, with nothing to configure.
- Each assistant has memory, skills and self-learning, and acts in the applications with its owner's rights, through the platform's API gateway, asking before it acts.
- The service reaches the outside world only through APISIX, but for its PostgreSQL database and, from the worker role alone, the RabbitMQ broker over AMQP; it keeps the assistants' encryption secrets in the platform's OpenBao, and logs every action with its metadata at `info`, the conversation itself (prompt, answer, reasoning, tool arguments and results) only at `debug`, so the messages it decrypts stay out of production logs; of the arguments of a call, only the `from` and `days` of a `list_calendar_events`, in the shape the contract takes them, reach `info` (see Time zone).

## Stack and conventions

Aligned with `twake-workplace-common-settings` wherever it has an opinion: TypeScript in strict mode as ES modules, npm, Vitest, Drizzle with postgres.js, zod, ESLint flat config and Prettier with tabs. The HTTP layer is Fastify: common-settings is a SvelteKit application and carries no backend framework, Fastify is the server already used in Twake backends, and its pino logger writes the JSON lines with a request id that the spec requires. Node 22.

Code follows the Twake JavaScript and TypeScript conventions: named exports only, explicit types on exported symbols, `unknown` for external data, no enums, `#` for private members, comments only for business reasons.

## Roles

One image, one role per deployment, chosen by `HARNESS_ROLE`:

- `api` serves the HTTP API behind APISIX.
- `worker` runs the daily curation: for every owner, under their own principal, it merges duplicate memory entries and turns a request made the same way in three conversations or more into a skill proposal for that owner. With `ACTIVITY_ENABLED` or `CALENDAR_ENABLED`, it also listens to the activity exchange of RabbitMQ or to Calendar's fanout there, the only role that connects to the broker (see The activity exchange, and Calendar's invitations). Every hour, listening or not, it forgets the wake-ups past their retention, and purges the listening journals (see Listening journal). Every day at `DELEGATION_REMINDER_HOUR`, it reminds the owners whose permission for their assistant to act for them is about to expire (see Consent). It serves its health check and its metrics, and nothing else.
- `matrix` is the Matrix application service: it receives what Synapse pushes, answers as the creator user and the assistants, and calls Synapse through the `matrix` route of APISIX. Once an assistant is deleted, it asks the token broker to revoke its owner's permission for it to act for them (see Consent). `npm run matrix:registration` prints the registration file Synapse loads, given `MATRIX_APPSERVICE_URL`, the APISIX route Synapse pushes to. Its users namespace also holds the channel listener (see Suggestions): a deployment that already loaded an older registration applies the new one on Synapse, and restarts it, before it turns suggestions on.

The Matrix tests start a real Synapse in a container, so Docker is needed to run them.

### Behind the gateway

The api role is meant to sit behind APISIX only. With `GATEWAY_SHARED_SECRET` set, every request of the API must carry that value in `x-twake-gateway`, which the gateway injects on what it forwards; anything else gets a 403 before any identity work, while the health check and the metrics stay open to the cluster. The gateway writes the audit record of every contract call, one per call (agent, user, contract, method, path, status); the harness forwards the correlation id of the turn in `x-correlation-id`, so the record links back to it, and posts no record of its own.

### Replaying against dev

`npm run test:dev` replays the prototype's black-box checks (identity, default rights, memory and session isolation, identity override, two users at once) against a deployed harness through its gateway, with no database or container: set `HARNESS_BASE_URL` to the api route (for instance `https://apisix.dev.twake.lin-saas.com/agents`) and `HARNESS_TOKEN_A` and `HARNESS_TOKEN_B` to the access tokens of two users carrying the `twake-harness` audience. The results land in `dev-results/vitest.json`, to keep with the pilot. Without those variables the suite is skipped.

### Jobs between roles

The roles hand work to each other through the `jobs` table: a Matrix message becomes a `turn` for the api role, its answer a `send` for the matrix role, and each action of the turn a `progress`, which the matrix role shows its owner while the turn works: the counts of a room have a group of their own, so that none holds an answer back, even when no matrix role takes them, as during a rollout. Any replica claims any job (`for update skip locked`), so the api role scales horizontally; the chart ships a horizontal autoscaler for it (`autoscaling.enabled`), never below one replica. A job carries a dedup key, so an event Synapse delivers twice makes one turn, and a group key: the turns of one owner and the answers of one room run one at a time, in the order they were queued, whichever replica takes them. A deferred job is the exception: the turn of an event that admission refused waits out of its group's way, and comes back at the end of its group once due (see Admission), so that its owner's own turns never wait behind it, at the cost of telling such events out of the order they were published in. A job still running after its lease (fifteen minutes) is handed back to the queue, as its replica is taken for gone.

### While a turn works

The owner sees their assistant at work on a message, or on the yes that resumes a turn: eyes (👀) on it and the assistant typing, then a check mark (✅) beside the eyes once it is answered. The eyes stay: in an encrypted room, the homeserver keeps a redacted reaction as an empty encrypted event, which some clients show as a message they cannot read. A turn that has not answered after `TURN_STATUS_DELAY_MS` also posts a status message, "⏳ On it…" in the owner's language, as a reply to that message and encrypted like every other, which then counts the actions the turn has done, "⏳ On it… (3 actions done)", in edits at least that delay apart. The answer, or the notice of a failed or refused turn, then goes out as a message of its own, as it always did, and the status closes on "✅ Done", "⏸️ Limit reached" when the turn stopped at its limit of tool calls or of tokens, or "❌ Not done" after a notice, as an edit (`m.replace`) that Twake Chat marks as edited: Synapse's default push rules notify nobody of an edit (`.m.rule.suppress_edits`), and the owner is to be notified of what came of their message. A turn that ends on a question to its owner keeps the question a message of its own, which they answer in their next message, and the status then tells them to answer below. A status never outlives its turn: with no reply ready five minutes after the message, as long as the typing lasts, or, on a yes, `TURN_EVENT_MAX_DELAY_MS` later, as long as admission may keep the turn it resumed waiting to start, or none gone out five minutes after it was ready, or when the matrix role stops, it says that this takes longer than expected, and an answer that comes later goes out as a message of its own.

### Admission

A turn is admitted before any model call. The turns per minute of a user, those of the whole harness and the daily tokens of a user are counted in the database, so the limits hold whatever the number of replicas; the turns in flight, the queue of a full replica and the slots a user holds in it are each replica's own, as are the counters of `/metrics`. A refused turn gets a 429 with its reason, and in a room a notice in its owner's language of why and when to send the message again: their tokens of the day spent, until midnight in `ASSISTANT_TIMEZONE`; too many of their turns at once, over their turns per minute or past the queue of a full replica, for a minute; too many turns on the whole harness, for a moment.

The turns activities wake and the briefs may spend part of their owner's day alone: `CHAT_RESERVE`, half of it by default, is kept for the owner's own words, which may spend the whole day. Admission counts the tokens of each day spent by turns activities woke and by briefs apart from the total, and refuses those with the reason `event_share` once they spent `(1 − CHAT_RESERVE)` of the daily tokens. The owner's words, a yes that resumes a call included, and the suggestions spend the whole day alone, and no share cuts them. A turn an activity woke that admission refuses for that share, or for the owner's day spent, is neither deferred nor given up: its activity is kept for the brief, `share_spent` in the listening journal, and the next one is admitted the next day. A brief refused for the same reasons goes out all the same, laid out by the harness with no model call (see Morning brief). The first time that share refuses a turn an activity woke or a brief in a day, out of the owner's quiet hours (see Quiet hours), the assistant tells its owner, in their language, that it reacts to nothing on its own until midnight, that their next brief will name what comes until then, and that it still answers them; once a day, kept with the day's tokens, with a `share spent notice queued` line.

A turn an event woke tells its owner nothing when admission refuses it by rate or a full queue, since they asked for none of it: it is deferred, tried again two seconds later, then twice as late each time up to a minute, the window of the turns per minute, until `TURN_EVENT_MAX_DELAY_MS` after admission first refused it, an hour by default. Refused past it, the turn is given up and logged as `event turn abandoned`. A turn queued long before, as during an outage of the api role, still waits that long from its first refusal once the role is back. A deferred turn holds back none of its owner's other turns and comes back after them: the events of a burst may then reach the owner out of the order they were published in, while the owner's own messages never wait behind them. The chart renders `config.turnEventMaxDelayMs` as `TURN_EVENT_MAX_DELAY_MS` on the api role, which runs the turns, and on the matrix role, which keeps the status of a turn a yes resumed that much longer, only when set.

The limits are the `ADMISSION_*` variables of the configuration. The chart sets each one from its `config.admission*` value (`admissionMaxInflight`, `admissionUserQueue`, `admissionUserPerMinute`, `admissionUserDailyTokens`, `admissionGlobalPerMinute`) only when that value is set, as a whole number, and `CHAT_RESERVE` from `config.chatReserve` only when it is set, as given, `0` included. One turn that calls several contracts can use tens of thousands of tokens, since every model call sends the conversation again, so a deployment where people test often may need a larger daily budget per user.

### Encryption

The assistants' rooms are created encrypted and every message in them is encrypted end to end. The matrix role holds one encryption store per assistant on its volume, acts as each assistant's device through the application service (device masquerading, MSC3202), and receives the key shares Synapse pushes with the transactions (MSC2409), so no assistant runs a sync loop. Both flags are enabled on the Synapse the harness is registered with. The fallback, had push proved unworkable, would have been one sync loop per assistant; it was not needed. An assistant's encryption state is prepared when the role starts and when it is invited. Synapse pushes again the messages of a transaction the role missed, but not its key shares: while it holds the role for down, as it does for a while after the role stopped, it pushes no to-device message at all, and keeps them in the device's inbox until the device syncs past them. The assistant's device reads its inbox once its encryption is ready at the start of the role, so that the key shares of the messages written meanwhile are there before those messages come, and again whenever a message fails to decrypt, after which the message is decrypted again; each read goes page after page until nothing is left, from where the last one stopped, which the role keeps across restarts, and lets Synapse drop what it read; a read that stops at its safety net of a thousand pages goes on from there at the next start or the next failure. The messages written while the role was away are then answered once it is back.

In an encrypted room, an assistant, the organization agent included, takes a turn only from a message that reached its device encrypted, and the creator a command only from one that reached it encrypted: one in the name of the owner, or of a member, that came in clear was written on the server side, by a component or by anyone holding their token, and does nothing; the matrix role logs it. A room is encrypted when the encryption store of the assistant, or of the creator, says so: the SDK reads the room's `m.room.encryption` state and keeps it, since encryption is never turned off, and encrypts their own messages by it. The SDK takes a state it failed to read for no encryption, so a room it does not hold as encrypted is read again before a message in clear is heard: only the homeserver's answer that the room has no such state makes the room clear, and a room whose state cannot be read, the homeserver failing or refusing to answer, counts as encrypted, the message being logged with that reason. A room opened without encryption, as a member may open one with the organization agent, is heard as before.

Every assistant device is signed by the assistant's own cross-signing identity, which the harness holds whether the escrow is on or not: Twake Chat sends the room keys only to the devices that the owner of a cross-signing identity signed, so an unsigned device never reads its owner's messages. The identity is created when the assistant first speaks, or at once when a provisioner asks for the assistant (see Provisioning API). An identity on the assistant's Matrix user that the harness does not hold, such as one another application left there, is replaced, and so is the harness's own when its store is lost and no escrow keeps it. The cross-signing keys go up as the application service, which Synapse lets replace an identity without interactive authentication; the device's own token could not. The database keeps the master public key the harness holds, to tell its identity from any other.

### The owner's sessions

An assistant takes its owner's words, in each of its rooms, a message that starts a turn, names a command it answers itself or answers a question of the harness, or a reaction that answers one, only from a session of theirs that their cross-signing identity signed, and only from the identity it holds for them: the first one it saw published for them, kept in the database. The matrix role decrypts the event again with the assistant's own encryption engine, which tells the device the room key came from, queries the owner's keys as the homeserver publishes them, and checks every signature itself: the device's own, the self-signing key's on the device, the master key's on the self-signing key. A session that no identity of the owner signed, or that another identity than the one held signed, does not count as theirs. Twake Chat sets an identity up at the first sign-in and signs every later session with it, from the recovery key it keeps for its user.

`OWNER_DEVICE_TRUST` says what becomes of the words of another session. With `enforce`, nothing comes of them: no turn, no answer, a call waiting for the owner still waits; the matrix role logs the session, never the words, and the assistant tells the owner in their language, at most once a minute per session, why and what to do: verify that session from another one in Twake Chat (Settings > Devices, Verify), sign in to Twake Chat again when their account has no identity at all, or accept their new identity (below). A check that cannot be made, the homeserver failing to answer, takes nothing either, and the owner is told to try again. Words that came in clear, in a room of the assistant that reads as clear, take nothing either, and the owner is told why; `report` takes them as before, and logs them. With `report`, the default, the words count as before, while the matrix role logs, for every message of an owner, the session it came from, whether their identity signed it and whether that identity is the one held, and the assistant tells the owner once per session that it is not verified, and how to verify it. The identity is held in either mode. Encrypted words count once: the same ones under another event, a copy, start nothing in either mode, and the matrix role logs them; it remembers what it received for thirty days. As a copy older than that would count again, the words of a Megolm session whose first words the check decrypted more than thirty days ago start nothing either, in either mode, and the owner is told to send `/discardsession` in the room, which has their client start a new session, then to send their words again; clients start a new session at least weekly by default, Twake Chat after a week or a hundred messages. A session counts from the first of its words the check decrypted, so one that was idle when this rule was deployed counts from its next words. Report mode takes words only once the check decrypted them as new words: a check that fails before, as when what tells copies apart cannot be read, takes nothing, and the owner is told to try again. Whenever their words are not taken, in either mode, the owner is told, at most once a minute per session. The creator conversation takes an owner's commands under the same rule and the same setting: a command that came in clear in an encrypted room takes effect in neither mode, and is only logged (see Encryption); otherwise, with `enforce`, a command takes effect only when it came encrypted, from a session their identity signed, and the owner is told why when it did not; with `report`, every command takes effect as before, and the creator logs and tells the owner as the assistants do. The organization agent, which acts for no owner, hears its members as before.

An owner who resets their identity, so that their sessions are signed by a new one, has their words refused with `enforce` until they accept the new identity through the API, with their own token and the `chat` right; no message in the chat can, and the assistant tells them so. With `report`, their words count all the same, and their assistant asks them, in the room their words came to from a session the new identity signed, whether they reset it themselves: a question marked for their client, which waits for their answer as long as a consent request does (`CONSENT_REQUEST_LIFETIME_MS`). Yes makes the new identity the one held, as the API does, but only while the deployment reports: with `enforce`, an identity held by a yes in the chat counts no more than any other new one, words from it are refused, and once they came from a session it signed, `published` shows it for the owner to accept through the API. No keeps the one held, and the assistant advises them to change their password and warn their administrator; their words from the new identity still count, and the next of them tells them, once per session and per new identity, that the assistant still flags them. Answered no or not at all, the question is asked again at their next words from a session the new identity signed once it expired, so that a no given by mistake can be taken back. Their next message answers it or closes it to typed answers, as for a consent request; when a consent request was asked in the room after it, whenever its call froze, or asked there again, as when admission kept a yes to it from running, that request, the newest question of the room, takes the answer. Words from a session the new identity did not sign count as well, and the owner is told, once per session and per new identity, to write from a session it signed, or to verify this one, so that their assistant can ask them. The creator asks nothing: it tells an owner who writes to it from a new identity, once per session and per new identity, to write to their assistant, which asks them in its room, or, when they have none, what to do if they did not reset it. Nothing `report` tells them names the API, which only `enforce` needs. `GET /v1/assistants/me/owner-identity` answers with the identity held, `pinned` (its master key, `pinned_by` `first_use`, `api` or `chat`, and `pinned_at`), and with the identity that signed the session their words last came from, when it was another one, `published` (its master key and `seen_at`), null otherwise. `PUT /v1/assistants/me/owner-identity` with `{ "master_key": "..." }`, the key `published` shows, makes that identity the one held (200); any other key gets a 409 with both. Both work for an owner who has no assistant yet, whose commands the creator takes under the same rule.

### Identity

One person is one principal everywhere in the harness: the subject of their platform token, which is their email. A user of the homeserver is that same person: `@alice:<MATRIX_SERVER_NAME>` is the principal `alice@<MATRIX_MAIL_DOMAIN>`, and the mail domain defaults to the server name. The creator conversation, the API, the email by which an event from RabbitMQ names its recipient and the owner header of the contract calls all carry that principal, so the assistant created from Twake Chat is the one the API returns for the owner's token, and a delegation keyed by email at the gateway matches. A principal of another mail domain has no account on the homeserver, so no room can be opened for it: the API refuses to create its assistant with a 422.

### Organization agent

With `ORG_AGENT_ENABLED`, the matrix role runs one more bot, the organization agent: a Matrix user in the assistants' namespace (`ORG_AGENT_LOCALPART`), with its own name and persona, that joins the direct messages of the members named in `ORG_AGENT_MEMBERS` and nobody else, greets them, and answers each of them with the member's identifier in front of the message. It acts under the organization principal, `org`, so its memory is the organization's and its skills library is the organization's; no token can carry that subject. Its contract calls carry no owner header: the gateway sees the harness key alone.

### Events

Events reach the assistants from RabbitMQ alone, which the worker role listens to: the `activity` exchange, where the applications publish their CloudEvents, and Calendar's fanout of the invitations it sends (see below). Each event comes with its turn, in the room of the owner it is for: the model is handed what the event says, and never reads it again through the contracts. Its system prompt tells the model that it may answer nothing at all when nothing in the event is useful to its owner, and otherwise to suggest it in a few words, preparing at most one action: a turn that ends on no words posts nothing in the room and keeps nothing of itself in the conversation. The turn the owner's yes resumes from it, as any turn of theirs, still ends on words, or on the notice of a failed turn when the model writes none. The harness takes no event over HTTP: `POST /v1/events`, through which a dispatcher posted events, is gone, and a deployment that still sets `EVENTS_CLIENT_IDS`, the service clients it took them from, starts as before and ignores it. The chart no longer renders it, and a release that still sets `config.eventsClientIds` renders as before.

### The activity exchange

With `ACTIVITY_ENABLED`, the worker role reads the `activity` exchange of RabbitMQ, where the applications publish their CloudEvents, as ADR 001 and 006 shape them, through `@linagora/rabbitmq-client` as Twake Tasks does. It declares a quorum queue of its own, `<RABBITMQ_PREFIX>.activity`, with a single active consumer, so that events keep their order whatever the replicas, a delivery limit of five, a consumer timeout of a day, at-least-once dead lettering into its own exchange `<RABBITMQ_PREFIX>.dlx` and queue `<RABBITMQ_PREFIX>.activity.dlq`, and reject-publish overflow. The consumer timeout keeps the broker from taking back an event the worker holds while it tries it again, which would count as a delivery, after the half an hour RabbitMQ 3.13 gives by default; it is an argument of the queue, since the instance's user may set no policy, and holds for a queue declared with it. It binds that queue to the types of `ACTIVITY_TYPES` only, and to its own dead letter exchange under its own name, which keeps its dead letters' key the same whatever the types. It never declares the `activity` exchange, and only checks that it is there: its RabbitMQ user may configure and write `^<prefix>\.` and read `^(activity|<prefix>\..+)$`, and nothing more. A queue keeps the arguments it was declared with. A type taken out of `ACTIVITY_TYPES` keeps its binding, which the library never removes, until it is removed on the broker; meanwhile the worker takes its events and drops them. Dead letters moved back into the queue come by its own name, and are read as the other events.

The worker reads one message at a time. Each recipient of the event's `data.recipients`, whatever its reason, is woken when their email, lowercased, is on the mail domain, as for the principals (`MATRIX_MAIL_DOMAIN`, or else `MATRIX_SERVER_NAME`, without which the harness refuses to start listening), when they have an assistant with a room, when their assistant listens to the application the event comes from (see Listened sources), and when they are not the event's actor, by email or by uuid: a task they assigned themselves, or that their assistant assigned them on their yes, as them, wakes them not, and their listening journal keeps it for their brief (see Listening journal), while their other own actions leave nothing. Their assistant gets a turn of origin event in that room, serialized with their other turns: the model is told what arrived, in the owner's language, a task assigned to them or an event of another type, and handed the event as one line of JSON between fences of a random nonce, what the application computed (type, ids, key, link, time, actor, reason) apart from what people wrote, under `untrusted` (title, board name, preview). Whatever that turn prepares to write waits for the owner's yes (see Consent), and its contract calls carry the bare id of the event as their correlation id. A wake-up is kept by the event's source and id and the owner it woke, in the transaction that queues the turn, before the message is acknowledged: a redelivery, a restart or a replay of the dead letter queue wakes nobody twice, and two recipients of one event are each woken once. The `wakeups` table holds identifiers and dates only, and nothing of a recipient without an assistant. Each recipient is read on its own: one with a malformed email, uuid or reason is left out, and logged by its place and the names of its faulty fields, never their values, and past the first hundred the others are left out with a log line that counts them. Text other people wrote is cut rather than refused, at 1,000 characters for a title or a preview and 200 for a board's name, and an optional field the application got wrong, such as a link that is no http or https URL, is left out and named in a log line. Only a message that is no CloudEvent with an id, a source, a type and its `data.object` goes to the dead letter queue, at once.

An event that fails holds back none of those behind it, and is never lost. A transient failure, the database out of reach or a connection lost, is tried again for as long as it lasts, the wait doubling from a second up to a minute, and never sends the event to the dead letter queue; any other failure is tried five times in all, with the same waits, then the event goes there and the next ones go on. A message that brings the worker down whenever it holds it goes there too: at the last delivery the queue allows, after it came back five times, as the broker counts them in `x-delivery-count`, the worker dead-letters it itself, rather than leave it to the broker with no line to say so. Once its cause is fixed, the dead letter queue is replayed by moving its messages back into the queue, with a shovel or the management UI: a replayed event wakes nobody it already woke within the retention, and a dead letter replayed after it, older than `WAKEUPS_RETENTION_MS`, may wake its owners again. Each message gives one JSON line once the worker is done with it, `event handled`: the event's source, id (`eventId`) and type, how many recipients it names, its `outcome`, and under `outcomes` how many of its recipients had each, `woken`, `capped`, `quiet_hours`, `for_brief`, `duplicate`, `unlistened`, `no_assistant`, `ignored`, or `invalid` for one it cannot read. The outcome of the message is the first of these one of its recipients had, or `ignored` for an event of a type it no longer lists, or `dead_lettered`, with the `reason`: `not JSON`, the attribute at fault, such as `no source` or `no data.object`, `failed 5 times`, or `delivery_limit`. Each failed attempt gives an `event failed` line, which says whether the failure is `transient`. No line carries what an event says, at any level: the library's lines go out without the bodies and the parse errors they would quote, and those the worker's own lines restate, at debug.

A broker out of reach, one that never answers, or an `activity` exchange missing never stops the role: the worker serves its health at once and listens in the background, and tries again without end, the waits doubling up to a minute, each failed attempt logged as `listen failed`, its connection closed. Each connection to the broker has ten seconds to open, or the milliseconds of `connection_timeout` in the query of `ACTIVITY_AMQP_URL`, as RabbitMQ's URI spec names it: a broker behind a firewall that drops packets would otherwise hold it for the minutes the system takes to give up. Once it listens, the library connects again by itself when the broker goes and comes back, and reads the queue again; when it cannot, the worker starts over as at its start. The worker's health check says whether the listener reads its queue, `"activity": "connected"` or `"disconnected"`, and answers 200 either way, so that a broker down never restarts the role. A known limit: the `activity` exchange deleted and declared again while the worker listens takes the queue's bindings with it, and the worker, still connected, says so, while no event reaches its queue; it binds the queue again when it connects again, so a restart of the worker role, after such a change on the broker, brings the events back. The worker forgets the wake-ups older than `WAKEUPS_RETENTION_MS`, 30 days by default, at its start and every hour, and logs how many went: within the retention, a redelivery or a replay wakes nobody twice, and after it the event is a new one.

An owner is woken at most `WAKEUPS_PER_HOUR` times in a rolling hour, 20 by default, whatever the source, counted in the `wakeups` table, so that a burst, a mass assignment or what piled up during an outage, drowns neither their room nor their quota: past it, an event wakes them no more, is taken from the queue all the same, is logged as `event capped`, and their listening journal notes it `capped` (see Listening journal), which keeps it from waking them later. A redelivery stays a duplicate, whatever the count. The chart renders `config.wakeupsPerHour` as `WAKEUPS_PER_HOUR` on the worker role, only when set.

The chart renders these settings on the worker role only: `config.activityEnabled`, the URL from `config.activityAmqpUrlSecret` and `config.activityAmqpUrlSecretKey`, by default `ACTIVITY_AMQP_URL` in the chart's own Secret, `config.activityTypes` and `config.rabbitmqPrefix`, and `config.wakeupsRetentionMs`, whether the worker listens or not; it refuses a listening worker without `config.matrixServerName` or `config.matrixMailDomain`, which every role gets when set. With `networkPolicy.rabbitmqNamespace`, it lets that role alone out to the broker's namespace, on `networkPolicy.rabbitmqPort` (5672). The suite runs a RabbitMQ 3.13 container, as on dev, from `RABBITMQ_IMAGE` when set.

### Calendar's invitations

With `CALENDAR_ENABLED`, the worker role also reads Calendar's own fanout, `calendar:event:notificationEmail:send`, on the vhost `CALENDAR_AMQP_URL` names, `calendar` on the platform, where Calendar's side service sends a notification for each invitee of each change to a meeting: the invitations of personal calendars never reach the activity exchange. It reads it on a connection of its own, through a quorum queue of its own, `<RABBITMQ_PREFIX>.calendar`, which keeps the guarantees of the activity queue: one message at a time, a single active consumer, a delivery limit of five, a consumer timeout of a day, and at-least-once dead lettering into `<RABBITMQ_PREFIX>.dlx` on that vhost and `<RABBITMQ_PREFIX>.calendar.dlq`. It never declares the fanout: there too, its RabbitMQ user may configure and write `^<prefix>\.`, and read `^(calendar:event:notificationEmail:send|<prefix>\..+)$`.

The fanout carries every tenant's invitations: a notification for an invitee off the mail domain, or that names none, is foreign to the instance, taken without effect before anything else of it is read, and logged nowhere, even one that cannot be read, so that another tenant's invitations never reach its dead letter queue. Of the others, a new invitation wakes its invitee, `method` REQUEST in any case with `isNewEvent` true, and so does a move of a meeting they were invited to, a REQUEST without it whose `changes` name `dtstart` or `dtend`; one whose `changes` name the title alone, `summary`, is kept for their brief with no turn (see Listening journal). The cancellation of a meeting they were invited to, of one occurrence of its series or of the whole series, `method` CANCEL, wakes them too, whatever they answered it. An invitee's counter-proposal of another time for a meeting, `method` COUNTER, wakes the organizer it is for, and an invitee's answer, `method` REPLY, is kept for the organizer's brief with no turn, either only when its VEVENT's ORGANIZER names the person it is for: else it is taken without effect, its line saying `ignored` and `not the organizer`. `changes` loses `location` and `description` before anything else of it is read, and of the title only that it changed is read. A change to a meeting whose VEVENT gives the invitee's ATTENDEE the PARTSTAT DECLINED, or any other update, is taken without effect, its line saying `ignored`; that VEVENT is the meeting as the change left it, the one before coming with a counter-proposal alone, so that an invitee whose answer the organizer's client set back to NEEDS-ACTION as it moved the meeting is woken as one who never answered. The free text the harness never reads, DESCRIPTION, LOCATION, COMMENT, ATTACH and X-ALT-DESC, is taken out of the iCalendar first, with the lines folded onto it, so that none written wrong can set the invitation aside. ical.js then reads the rest, folded lines, escaped text, time zones, all-day dates and times in UTC included, and the invitation is its first VEVENT that is no occurrence, else its first. Its invitee, `recipientEmail` trimmed and lowercased, is woken as a recipient of the activity exchange is, for the reason `invited`, and its actor is its organizer, its ORGANIZER without `mailto:`, else `senderEmail`. The organizer a counter-proposal or an answer is for, its `recipientEmail` too, takes it for the reason `organizer`, a counter-proposal alone waking them, and its actor is the invitee, `senderEmail` trimmed and lowercased. The wake-up has the type `com.twake.calendar.event.invited.v1`, `com.twake.calendar.event.moved.v1` for a move, `com.twake.calendar.event.renamed.v1` for a new title, `com.twake.calendar.event.cancelled.v1` for a cancellation, `com.twake.calendar.event.countered.v1` for a counter-proposal or `com.twake.calendar.event.replied.v1` for an answer, the source `twake://calendar`, and the id the calendar producer gave the invitation, which the gateway's audit records carry as the turn's correlation id: the hex SHA-256 of its UID exactly as written, the person it is for, its SEQUENCE, 0 when it has none, and its RECURRENCE-ID exactly as written when it has one, joined with `|`, a cancellation adding `CANCEL` after them, a counter-proposal `COUNTER`, the invitee, and the DTSTART and the DTEND, or else the DURATION, it proposes exactly as written, and an answer `REPLY`, the invitee and the answer, so that a redelivery wakes nobody twice, none of them is taken for the invitation at its SEQUENCE, and each time an invitee proposes, and each answer they give, counts once. The model is handed the start, the end and the occurrence, as RFC 3339 times with the offset of their zone, the zone the calendar defines or else the IANA zone of that name, or as dates for an all-day event, the end being the start plus the DURATION when there is no DTEND, for a move the times it moved from, `previous_start` and `previous_end`, which `changes` gives as wall times in the zone it names, and the organizer's address; for a counter-proposal, in place of the start and the end, the time it proposes, `proposed_start` and `proposed_end`, and the invitee's address; apart from them, under `untrusted`, what people wrote, the organizer or, in a counter-proposal or an answer, the invitee's client: the title cut at 1,000 characters, the UID at 255 and the zone at 64. A field the calendar wrote wrong is left out on its own, and named in an `event fields left out` line, never with what it held; a notification without an iCalendar, a VEVENT or a UID the harness can read goes to the dead letter queue at once, its line saying why, and so do a counter-proposal or an answer whose `senderEmail` is no email address, an answer whose invitee's ATTENDEE gives none of the answers iCalendar names as its PARTSTAT, ACCEPTED, DECLINED, TENTATIVE, DELEGATED or NEEDS-ACTION, and one that is no JSON.

Before the model speaks, the harness asks `read_freebusy` about that slot, an all-day one from midnight to midnight in the owner's zone, the deployment's when none is kept (see Time zone), in the owner's name, with the invitation's exact UID left out, and hands the model the answer after the invitation, fenced as data; without a free/busy contract in the catalog, or for a slot it cannot ask about, such as one without an end or in a zone nobody knows, it says why it did not check, never naming the zone. No log line holds a UID or a zone. The first read of the owner's calendar waits for their yes, as any first read does. The model tells the owner who invites them, to what, when, and whether they are free, and prepares `accept_invitation` with the invitation's UID, which waits for the owner's yes (see Consent). The turn of a move says whether it moved a meeting, one occurrence of a series or the whole series, and checks the new slot, a series' from its DTSTART as an invitation's: the model tells the owner who moved which meeting, from when to when, and whether they are free over its new slot, and prepares `decline_invitation` when that slot conflicts, else `accept_invitation`, for a whole series as for a meeting, since only the owner's yes to the harness's question about a series sets `series` (see Consent). It is offered `read_freebusy` and those two answers alone, and no tool for one occurrence of a series, which the answers cannot reach apart from the rest of it: the model tells the owner they answer it in Calendar. The turn the owner's yes resumes is told of no event and keeps the tools of any event's turn. A move whose turn prepares an answer while the owner's yes to the meeting's former one is still awaited replaces that question, as any newer request does, so that the answer prepared for the former slot is never sent. The turn of a cancellation says whether it cancelled a meeting, one occurrence of a series or the whole series, checks nothing and is offered no tool: the model tells the owner in one sentence who cancelled which meeting and when it was to take place, and asks them nothing. The turn of a counter-proposal says whether it is about a meeting, one occurrence of a series or the whole series, and checks the time proposed as an invitation's slot, the meeting left out: the model tells the owner which invitee proposes which time for which meeting and whether they are free then, is offered `read_freebusy` alone, whatever the proposal is about, and prepares nothing, as the owner changes a meeting's time in Calendar. The listener copes with failures as the activity one does (see The activity exchange): a transient failure is tried again without end, any other five times before the dead letter queue, a notification back at its delivery limit is dead-lettered with its line, each one gives its `event handled` line, under the source `twake://calendar` and the id of its invitation, and no line carries what it says. A broker out of reach or a fanout missing never stops the role, `connection_timeout` in the query of `CALENDAR_AMQP_URL` sets how long a connection has to open, and a fanout declared again while the worker listens has the known limit of the activity exchange. The worker's health check says `"calendar": "connected"` or `"disconnected"`. The chart renders these settings on the worker role only: `config.calendarEnabled`, and the URL from `config.calendarAmqpUrlSecret` and `config.calendarAmqpUrlSecretKey`, by default `CALENDAR_AMQP_URL` in the chart's own Secret; the egress rule to the broker serves both sources.

### Suggestions

An assistant proposes an action from what is said in a channel: after « ok on parle lundi », « You are free on Monday from 9:30 to 9:45, schedule the meeting? », to the person who wrote it and to the person who wrote the message before it, each with their own assistant. The harness reads nothing of private exchanges, not even their metadata, but the encrypted conversation of two people where one of them brought their own assistant in and the other said yes (below): otherwise it sees only the rooms, neither encrypted nor direct, inside a space or not, that a visible user of its own, the channel listener, was invited to. No assistant joins any channel. Suggestions are off unless `SUGGESTIONS_ENABLED=true`: off, nothing below runs, and the listener declines its invites and leaves the rooms it is still in, at each start of the matrix role.

- **The listener.** One Matrix user in the application service's exclusive users namespace, `@<SUGGESTIONS_USER_LOCALPART>:<MATRIX_SERVER_NAME>` (`@twake-assistant:<server>` by default), registered at the start of the matrix role, when suggestions are on, and named « Twake Assistant » (« Assistant Twake » with `ASSISTANT_LOCALE=fr`). Synapse pushes the rooms it is a member of, and no other: the registration has no room namespace. Room admins invite it from Twake Chat, and a member list shows it. It never sends a message, in a channel or anywhere.
- **Which rooms it accepts.** On an invite it declines a direct room (`is_direct`) and a room whose stripped state shows encryption, without joining. Otherwise it joins and reads the room's state (as `roomEncryption()` would for an assistant, not through its crypto: the listener has no device): it stays, and reads the room for as long as it is a member, unless the room has an `m.room.encryption` (the stripped state may leave it out); else it leaves with the reason. It checks the same again for each room it is in when the matrix role starts. When a room it is in turns encrypted (an `m.room.encryption` state event, or an encrypted event), it leaves at once. Every room that is not encrypted, inside a space or not, is read continuously once the listener is in it; it never analyses an encrypted room nor a direct room: private exchanges are only seen when their user sends a message on purpose (« Ask my assistant »), or brings their own assistant in, as the next point says.
- **An encrypted direct conversation, by its owner's choice.** The listener never enters one. Its member may invite their own assistant into it, as Twake Chat offers after a warning (D128 there): invited by its owner into an encrypted room where exactly one other person is, joined or invited, and once that person accepted (Twake Chat's `app.twake.chat.assistant_request` of the owner and `app.twake.chat.assistant_consent` of the other person, each keyed by its sender with the assistant in `assistant_id`, the yes given after the request), the assistant joins and stays, greets no one, never takes a turn nor writes there, and reads what both write, for suggestions to its owner alone (`assistant_listened_rooms`). Chat shares no key of the history, so it reads what is sent from then on. Without that yes it leaves at once, without a word. It stops, and the room is forgotten, once it leaves or either member removes it; a third person coming in, either member leaving, a withdrawn request or a no makes it leave without a word.
- **The switch of a channel.** Kicking or banning the listener, or removing it from the room, stops the analysis of that room at once: this is the switch room admins use from Twake Chat. Nothing else is needed, and nothing of the room is kept.
- **The pre-filter.** A pure function (`src/suggestions/prefilter.ts`, French and English) runs on each clear message before any admission or request to Synapse: the message must name a date or time (a weekday, tomorrow, next week, 10h, 3pm, 12/10, 3 novembre) and show the intent to meet (on parle, on se voit, se voir, réunion, call, rdv, catch up, let's talk), and be 600 characters or less. Only then does it go further.
- **Context, in memory.** The matrix role holds the last message of each room in its memory only, as context for the next, for fifteen minutes: then it goes within the minute, whether a next message came or not. A model is handed the message that matched and the one before it, at most. The only place a quote is written is the payload of the `suggest` job, which carries it to the api role and is deleted when the model has answered or the job is dropped (a job over ten minutes old, or one that finds suggestions turned off, is dropped without being read; the handler never fails, so a failed job never keeps its quotes), or with the owner's assistant (see Consent). A job that waits for its owner to let their assistant read their calendar keeps them no longer: ten minutes from the message at most (see The model).
- **Who is offered something.** The author of the message and the author of the one before it, when they differ, each only if they have an assistant, have not turned suggestions off, have not muted the room, and are under their caps: three suggestions in a rolling day and one per room in twelve hours. Whoever turned suggestions off is never quoted: if the message that matched is theirs nothing happens, and their message is not quoted for the other; like any message of the channel, it is only held in memory as context (above). A suggestion needs the other person: a message alone, with no message before it, proposes nothing and asks nothing.
- **The model.** The job runs in the api role, outside any session: a fixed system prompt, the quotes as one fenced block marked as untrusted data with the author's address and the room, and only the contracts `find_meeting_slots` and `create_meeting`. When the owner never allowed an application that the suggestion reads, here their calendar, the job asks the first-use question in their assistant's room, in their language, saying that it is to propose a slot for a message of the other person, by address and with no quote, and waits for the answer, ten minutes from the message at most: a yes lets it go on, and a no, a newer question in that room or no answer by then drops it, quotes included. It asks once per application and level: not while a request for that permission waits, its own or one of the owner's turns, which it then waits for, and never again after a no, but again, for a later message, once its question expired or a newer request superseded it. The call frozen for that question holds nothing of the messages, and the owner's yes to it ends their turn on the harness's thanks: no model runs it, and no direct tool call can. The contracts decide what is asked: a write never is, since the meeting always waits for the owner. The code holds both calls to the messages, whatever the model writes: `find_meeting_slots` looks only at the calendars of the owner and of the people who wrote the messages, the attendees of `create_meeting` can only be those people, by their address, never one a message names, a declined slot is refused, and the meeting keeps its title, slot, zone and attendees alone, no description or place, so that the owner approves all of what they are shown. The turn's messages are dropped after it: nothing goes to history or memory. The model's call to `create_meeting` freezes as a pending call of origin `suggestion`, which waits for its owner whatever they allowed (it is a high-risk write), like the write of an event's turn; if the model prepares no meeting, nothing happens. The turn the owner's yes resumes in their assistant's room is still the suggestion's: it is offered these two contracts alone, held to the owner and the people the meeting invites, makes four calls at most besides that meeting, as a suggestion does, fewer when `TURN_MAX_TOOL_CALLS` is lower, and reads none of the owner's memory or skills; another meeting it prepares waits for them again. Nothing is ever posted in the channel.
- **Where the owner sees it.** In Twake Space, if `SPACE_API_URL` is set: `POST {SPACE_API_URL}/notifications/suggestions` with `Authorization: Bearer {SPACE_API_TOKEN}` and `{ "matrixUserId", "externalId", "text", "pendingCallId", "matrixRoomId" }`, where `externalId` and `pendingCallId` are the pending call's id, `text` the sentence the harness writes from the call (day, hours, title as plain text, the people invited, at most 500 characters, never the model's own words) and `matrixRoomId` the channel. A 201 or a 200 is done; a 200 with a null `id` means the user turned suggestions off in Space; a 404 (`unknown_user`) or a 403 is logged with its status and nothing else. Space's buttons call `POST /v1/pending-calls/{id}/approve` and `/refuse` with the user's token, whose audience may be one of `AUTH_ANSWER_AUDIENCES`, accepted on these two routes alone. The proposal is also written in the owner's assistant room, as an event's turn is, with the usual yes or no. Without `SPACE_API_URL` only the room has it.
- **Refusing.** `POST /v1/pending-calls/{id}/refuse` takes an optional body `{ "reason": "another_time" | "not_useful" }`. For a suggestion, `another_time` queues one new suggestion that excludes the slot refused, from the title and the attendees of the refused call (no message is kept to read again); a suggestion that was itself a second try is not tried a third time. `not_useful` mutes that room for that user for seven days, even when the suggestion was answered already, expired or replaced, which still gets a 409. A refusal without a reason, or of any other call, changes nothing more than it did.
- **Turning it off.** The organization, with `SUGGESTIONS_ENABLED`; a channel, for everyone, by removing the listener (above); a user, with `PUT /v1/suggestions/settings` `{ "enabled": false, "mutedRooms": [] }` (or their provisioner for them, see Provisioning API), which turns off both reading their messages and offering them anything, and a member can mute a room for themselves. `GET` shows the same: `mutedRooms` lists the rooms muted now, for good or after a refusal, and `PUT` replaces those muted for good.
- **What is kept.** A suggestion keeps its channel, its slot and whether it was a second try, never a message: for a day, which the caps count, or the lifetime of a request when longer, and as long as its call waits for the owner. The worker role's hourly pass forgets the others, and the mutes that ended. Deleting an assistant erases its owner's suggestions and those still to make, forgets the encrypted conversations it read for them, and keeps their switch and the rooms they muted, which are theirs and not their assistant's.
- **Logs.** The suggestion path logs identifiers, counts and outcomes at `info` (`suggestions queued`, `suggestion skipped`, `suggestion asks for consent`, `suggestion made`, `suggestion decided`, `suggestion sent to Space`, `suggestions switched`), never a message. A suggestion's turn logs nothing below `info`, whatever `LOG_LEVEL`: the prompt, which holds the quotes, and the arguments the model writes from them, which a turn logs at `debug`, reach no log. Nothing is used to train a model.

### Listening journal

Each owner's listening journal, under their own principal, notes the activities a source published for them that wake their assistant, that their hourly cap holds back, that their quiet hours hold, or that it keeps for their brief, from the activity exchange or Calendar's fanout: an activity's source, type and id, when it arrived on the worker's clock, what came of it, and what identifies and shows it. Of an object of the activity exchange, its type, id and key, and the title of a task or a meeting alone, never what a message or a file is called; of a meeting, its UID and RECURRENCE-ID, its title and its times, the times a move moved it from, the time an invitee proposes and their address, or an invitee's address and answer, never its place, its description or a comment. What came of it is `woken` until the turn it woke ends, then `suggested` once that turn answered, `nothing_useful` once it ended on no words, `abandoned` once it waited past `TURN_EVENT_MAX_DELAY_MS` for admission, `share_spent` once admission refused it as the owner's day, or the share of it their assistant spends on its own, was spent (see Admission), `failed` otherwise; `capped` when the owner's hourly cap held it back, or `for_brief` for a task they assigned themselves, a meeting's new title alone or an invitee's answer to a meeting they organize, which call for no word at once, both with no turn; `quiet_hours` while their quiet hours hold it, then `woken` once it wakes them as they end (see Quiet hours). An activity their journal noted wakes the owner no more, woken or not; a brief leaves no row. The owner's own turns have the `listening_journal` tool, which lists the activities received since midnight in their zone, the deployment's (`ASSISTANT_TIMEZONE`) until a read named one (see Time zone), with what came of each and their titles under `untrusted`; a turn an activity woke never has it. The worker role erases an activity's title and times after seven days, as the brief that names an activity does (see Morning brief), after which the tool gives its source, its type and what came of it alone, and deletes it after `WAKEUPS_RETENTION_MS`, at its start and every hour, with a `listening journal purged` line that counts both. Each activity gives one `activity noted` line at info once settled, from the worker for one capped, held for the quiet hours or kept for the brief and from the api role once the turn it woke ended: its source, id, type, owner and outcome, never what it says.

### Listened sources

Each owner chooses the applications their assistant listens to: Calendar and Tasks by default, Mail from their yes to the question of their first brief (see Morning brief), and Drive once they ask, unless they chose otherwise. An activity, from the activity exchange or Calendar's fanout, is the application's by the source it was published under: `twake://calendar` is Calendar's, `twake://tasks` is Tasks', and any other source, Mail, Drive and Chat included, publishes for nobody until the harness knows its producer, with an `activity of an unknown source, listened to by nobody` warning that names it. An activity of an application the owner's assistant does not listen to wakes nothing and leaves nothing, in their room or their journal, and takes none of their wake-ups: its recipient's outcome is `unlistened`. A brief is no activity. Mail and Drive publish nothing the harness takes: listening there wakes nothing, and only has the owner's brief read their mail, or the shares made to them, as their brief reads only the applications their assistant listens to (see Morning brief). The owner's own turns have three tools: `listened_sources` lists the applications their assistant listens to, those it could listen to but does not, and those it cannot listen to yet; `stop_listening_to_source` stops listening to Calendar, Tasks, Mail or Drive, which their assistant still reads when they ask; `listen_to_source` starts again. Listening to an application whose data the owner has not let their assistant read asks them first, with the question of a first read there, which shows the call: their yes lets it read there and starts listening, as any first read's yes allows the application from then on. Each choice ends the turn on the harness's own words, in the owner's language, which for Mail and Drive say that their brief alone tells of them, and gives a `listened source set` line with the source and whether it is listened to. The choices take the `settings.write_own` right, and a turn an activity woke has none of these tools. Migration 0092 has the assistant of every owner who had let it read their mail listen there, unless they had chosen for Mail already: their brief does not change.

### Morning brief

With `BRIEF_ENABLED`, the worker role wakes each owner's assistant for their morning brief, on the days and at the time they chose, Monday to Friday at 8:00 unless they chose others (see below). Every minute, it looks at each owner whose assistant is in its room, one after the other, on the wall clock of their calendar's zone, the deployment's (`ASSISTANT_TIMEZONE`) until a read named one (see Time zone), so that their brief keeps its time on that wall clock when the clocks change: on a day of their brief, from its time, it wakes their assistant through the wake-ups the events use, under the source `schedule`, the type `com.twake.harness.brief.v1`, and an id of each owner's date, `brief-<date>-` and 16 hex digits of a SHA-256 of the owner and the date, which the gateway's audit records carry as the correlation id of the brief's calls. A brief counts among the owner's `WAKEUPS_PER_HOUR`, and goes out once for each date, whether a pass runs again after a restart or on another replica; one their hourly cap held back is tried again at each pass, and logged `event capped` at the first of them alone, once in each worker process. A pass late by less than three hours still sends it; three hours past its time, a brief that never went is skipped, and the line `morning brief skipped`, once in each worker process for each time the owner chose that day, gives the owner, the date and the zone. A brief due after 21:00 has until midnight alone: one that never went by then goes no more, without that line. Another time they choose that day opens the day again from it, as a restart of the worker would; a brief that went never goes twice. The wake-ups kept are what holds a brief to once a date, so the harness refuses to start with `BRIEF_ENABLED` and a `WAKEUPS_RETENTION_MS` under two days. Only the scheduler's wake-up asks for a brief: an event published under the source `schedule` wakes nobody, and one of another source is an event's turn, whatever its type. With `BRIEF_ENABLED` off, the worker role's line `morning briefs off` says so once at its start, and its passes wake each owner's assistant for what their quiet hours held alone (see Quiet hours). The chart renders `BRIEF_ENABLED` on the worker role, and on the api role, which gives the owner their brief when they ask for it (below), from `config.briefEnabled`, `false` by default.

The owner sets their brief by asking their assistant, which calls `brief_settings`: `show` reads it; `time` sets the time it is due, `HH:MM` on their wall clock, on the quarter hour, any other refused; `days` sets every day of the week it goes out, one at least; `pause` holds it back until a date after today, on which it goes out again by itself; `stop` holds it back until they resume it; `resume` ends a stop and a pause alike. Every call whose arguments it can read answers the brief as it stands: its time, its days, the end of a pause under way, whether it is stopped, and the zone it follows. What they chose is kept next to their zone, in their own row of `owner_settings` under row-level security, and each pass reads it, so that a change counts from the next minute. The deletion of their assistant erases it with their zone: the next assistant's brief goes out by default, on the deployment's wall clock until a read names their zone again. The tool, to read the brief as to change it, takes the `settings.write_own` right, which a turn an event started never holds, and a turn that comes from others, an event's or a suggestion's, is never offered the tool, even once its owner's yes resumed it: nothing a third party writes moves or stops a brief. The organization agent, which has no brief, is refused. The tool is offered whether the briefs are on or not.

The brief's turn runs on the api role, admitted as a turn is; refused by rate or a full queue, it waits as an event's turn does (see Admission), its lines `brief turn deferred` and `brief turn abandoned` saying why. Refused as the owner's day, or the share of it their assistant spends on its own, is spent, it goes out all the same, laid out by the harness from the same reads with no model call, and its line `brief written` names the refusal, `refused`. Before the model, the harness reads itself, in the owner's name and with the checks of the model's own calls: the day through `list_calendar_events`, from the brief's date for one day, twenty meetings at most; the invitations that wait for the owner's answer through `list_calendar_events` again, from the brief's date for seven days with `needs_action`, a hundred occurrences at most, of which it keeps each invitation once, a series by its first occurrence, numbered from 1 in the order they start, twenty at most; then, in the zone kept for the owner once those reads named one (see Time zone), their unread mail: their inbox, the mailbox of that role among those `list_mailboxes` lists, then its unread emails through `list_emails`, since the instant the owner's last brief read them, or, before any did, since the same time of their wall clock on the last day before that they have a brief on, Friday for a Monday, fifty at most, newest first, of which it leaves out those sent in bulk; then their tasks through `list_my_tasks`, those overdue then those due today, thirty at most together, the overdue ones first; then the shares made to the owner through `list_received_shares`, since the instant their last brief read them, or, before any did, since the instant their mail is read from, thirty days back at most, twenty at most, newest first, each file and folder numbered after the invitations and the meetings the brief numbers, but those of a shared drive, which no other operation of Drive reaches. From the owner's listening journal it reads what had no turn and no brief named yet, the activities their hourly cap held back, that waited past `TURN_EVENT_MAX_DELAY_MS` for admission or that admission refused once the share of the day their assistant spends on its own was spent, those kept for their brief, such as a meeting's new title, and those their quiet hours hold: twenty at most, the first that arrived, of which it tells apart the answers to the owner's invitations, which their journal keeps for their brief, and the tasks they assigned themselves, kept for their brief as well. It reads only the applications the owner's assistant listens to (see Listened sources): without Calendar, neither the day nor the invitations, nor the activities Calendar published, and a brief that waits for the owner's answer about the day's read (below) goes out without it; without Mail, no mail; without Tasks, no tasks, nor the activities Tasks published; without Drive, no shares. Such a section is said to nobody, not even as not read, and the line `brief application skipped` gives it with `not_listened`. An application that needs a yes the owner has not given, here once their brief no longer asks for its reads (below) or on the token broker, is left out, and nobody is asked, but for the day's read the broker refuses (below): the line `brief application skipped` names its domain, `calendar`, `mail`, `tasks` or `drive`, its section, `calendar`, `invitations`, `mails`, `tasks` or `shares`, and why, `consent` or `delegation`, as it does a catalog without the contract, `unavailable`, a read that failed, `failed`, an answer the harness cannot read, `unreadable`, or mailboxes none of which is the inbox, `no_inbox`; the mail is left out when either of its reads is, and the tasks likewise. One model call follows, with no tool and no history, after the assistant's persona and the present: the assistant is told its owner's day is starting, in the owner's language, and handed what the reads gave as data, fenced: the day, each meeting's times, status, answer and overlaps as the contract computed them, and under `untrusted` what people wrote, its title, location, description and organizer; the invitations, each with its number and whether it is one of a series; the mail, the instant it is read from, `since`, its emails as the contract gives them, in the order the harness lays them out (below), what Mail computed, whether one is flagged, sent in bulk or sent to the owner, `to_me`, included, and under `untrusted` its sender, subject and preview, whether Mail had more, `truncated`, and the addresses of the people the day's meetings name, their organizers but the owner, `participants`; the tasks as the contract gives them; what arrived since the owner's last brief, `since_last_brief`, when anything did, each activity as the `listening_journal` tool shows it to a turn, a meeting with its number, the number of its invitation when the brief numbers it too, the next ones otherwise, a task with its key, and whether the journal had more, `truncated`; the answers to the owner's invitations, `replies`, each as that tool shows it, with the number of its meeting, given as for what arrived since the last brief, the declines first, then the maybes, the other answers, and the acceptances last; the shares, the instant they are read from, `since`, each share as the contract gives it, what Drive computed, whether it is read only or a shared drive, its files and folders, each with its number but in a shared drive, and under `untrusted` each one's name and who shared it, and whether Drive had more, `truncated`; the tasks the owner assigned themselves, `self_assigned`, each as that tool shows it, with its number, after the shares', and its key; and, for a section not read, why, under `not_read`, but for an application whose read the owner took back, which the harness tells them of itself (below), and one their assistant does not listen to. It is asked for those sections in that order, five items at most each, then how many more there are, a section with nothing in it or not handed left out but for the day, when handed, which says in one line that there is no meeting; of the emails, for those flagged first, then those sent to the owner that ask a question, make a request or give a deadline, or that come from someone of the day's meetings, then how many more are unread; of the answers, for the declines and the maybes named first, then the acceptances counted; and, when it showed invitations, emails, tasks or shared files, for one or two examples of what the owner could answer with their numbers, keys or senders. The brief is an ordinary `m.text` message, which notifies, marked `app.twake.assistant.brief` with `{ "date": <date> }`. As it repeats what people wrote, unasked, it mentions nobody (an empty `m.mentions`, whatever `@room` its text holds), and its HTML renders the model's Markdown as the harness quotes the model in its requests: no link, image, heading or HTML of its own, a link showing its text alone. The conversation keeps it as the assistant's answer, which the owner's next turn reads in its history after the intro the assistant was told and, fenced as data, what the brief's numbers, its tasks' keys and its emails name: the `uid` and `recurrence_id` of each invitation, the `id` and sender of each email the model was handed, whichever it showed, in the order the harness lays them out, the `board_id` and `task_id` of each task, and under `since_last_brief` the `uid` and `recurrence_id` of each meeting that arrived since the last brief, by its number, and the `task_id` of each task, with its key, under `replies` the `uid` and `recurrence_id` of each meeting answered, by its number, under `shares` the `id` and type of each file and folder shared with the owner, by its number, and under `self_assigned` the `task_id` of each task the owner assigned themselves, with its key, by its number. "Decline 2" is then an ordinary turn, with its rules. A newer brief takes them out of the earlier one, which the conversation keeps otherwise; the data a brief was written from stays out of the conversation. Its tokens count in the owner's day. Should the model fail or write nothing, the harness lays out the same sections itself, marked too, in the owner's language: the meetings, each one's times as the calendar gives them and its title, and the titles of the meetings it overlaps; the invitations by their numbers, each one's title, day, times or whole day, a series from its first date, and who invites; the unread emails since the day and time they are read from, flagged ones first, then those sent to the owner, then the latest, each by its sender's name, or else address, and its subject, a flagged one said so, and that more are unread when Mail had more, even when all it gave was sent in bulk; the tasks by their keys, each one's title and the day it was due, or the time it is due today; what arrived since the last brief, a meeting by its number and a task by its key, each one's title and what it was, an invitation, a move, a new title, a cancellation, a counter-proposal, a task assigned to them or another activity; the answers to the owner's invitations, each by its meeting's number and title, who answered and what, the declines and the maybes named, then how many accepted; the shares, each file and folder by its number, but in a shared drive, said so, a folder said so too, and who shared it, by their name, or else address, or else as someone; the tasks the owner assigned themselves by their numbers, each one's title and key; five items at most a section, then how many more there are, a section with nothing in it left out, a day without meetings in one line, an application not read in one line, but one whose read the owner took back or that their assistant does not listen to, and two examples at most of what to answer, drawn from the invitations, emails, tasks and shared files it shows; people's text is text, never markup. The line `brief written` says who wrote it, `model` or `template`, how many meetings, invitations, emails, tasks, activities, answers to the owner's invitations (`replies`), shares and tasks the owner assigned themselves (`self_assigned`) it was written from, and the tokens. The instants a brief read the owner's mail and the shares made to them are kept in their own row of `owner_settings`, in the transaction that keeps the brief, for their next brief to read from; a brief that did not read one leaves it as it was. In the same transaction, the activities the brief was handed lose their title and times, and an answer who gave it and what it was: the next brief names them no more, and the `listening_journal` tool tells them by their source, their type and what came of them alone; those the owner's quiet hours held come out of the hold, and wake nobody as they end.

The day's read the token broker refuses for want of the owner's permission for their assistant to act for them, `delegation_missing` or `delegation_expired` (see Consent), is the exception: the brief reads nothing else and gives way to the harness's own request about that permission, the one a turn ends on, with the consent link and the offer to try again, in one message marked as a question, and no model call; the line `brief gave way to a question` names its call. That brief waits for the owner's answer, and the next ones say nothing until the day's read works again, whether the broker still refuses it, the gateway fails it or the harness does not make it: their day is read, without asking again, and the line `brief withheld` names the call and the date the brief waits since. The owner's yes, once they gave the platform their permission, runs the day's read again as it was frozen, under the brief's id, then the brief's other reads, and that day's brief goes out in answer to it, admitted as the morning's brief is, marked with its date, at whatever hour the request still lasts; a yes the broker still refuses gets the request again, which supersedes the one it answered. Their no drops the call as any no does, and the briefs still say nothing until the day's read works again; so does a request left unanswered until it expires. A brief that goes out ends the wait: once the day's read works again, the next morning's brief comes back by itself, asking nothing, and the request it gave way to closes as expired, so that a yes to it runs nothing and is told so. The harness keeps one waiting brief per owner, its date and its call, which the deletion of their assistant erases.

An owner's first brief asks for its reads before it reads anything. Until their brief no longer asks for them, a brief whose owner did not let their assistant read their calendar, their mail or their tasks, at the `read` level each, reads nothing and goes out as the harness's own message, in the owner's language, with no model call, marked as a question: what their brief tells, the days and the time it goes out on and how to change them, then one question for the reads they did not allow, in that order, whose call waits for their answer as any request does, under the brief's id, with the tool, the contract and the domain `brief` and the reads it asks for as its arguments; the line `brief asked for its reads` names its call, the reads and how many times it was asked. The conversation keeps it as the assistant's answer. Their yes, in the room or through the API, allows each of those reads on its own, recorded as given where they gave it, which they take back one at a time as any other, has their assistant listen to their mail, unless they chose otherwise (see Listened sources), and that day's brief goes out in answer to it, marked with its date, at whatever hour the question still lasts, from its day's read on, as any brief; the line `brief reads allowed` names them. Their no stops their brief, as `stop` does, and the harness says so itself, with the words that resume it. Left unanswered, the question goes out once more, on the next day their brief goes out on, then the brief after it stops, as on a no, and says so, asking nothing, its question closing as expired, with the line `brief stopped: its question went unanswered`; a brief of a date that asked already says nothing, its line `brief withheld` naming the question's call. A resume asks again, as the first time. A brief that finds the three reads allowed asks nothing, and their assistant then listens to their mail only once they ask it to; the first brief to go out closes the question, should it still wait, as expired: their briefs ask for their reads no more. From then on, a brief goes without a read the owner took back, its line `brief application skipped` saying `consent`, and the first one to go without it says so after it, in a line of its own, with the words to have it read again, then nothing more of it, until a brief reads it again and the owner takes it back once more. Drive's read, which the question never asks for, is the exception: a brief that goes without it for want of the owner's yes says nothing of it. The harness keeps one question per owner, its date, its call and how many times it was asked, and, in their own row of `owner_settings`, whether their brief still asks for its reads and those it told them they took back; the deletion of their assistant erases them, so that the next assistant's first brief asks again.

A brief nobody reads is of no use: once ten working days, Monday to Friday, went by without the owner being seen in their assistant's room, the one their brief goes to, their brief stops, as `stop` does, and says so, with the words that resume it, asking nothing and reading nothing, with the line `brief stopped: its owner was not seen`. The owner is seen there by any message of theirs, with words or not, and by any public read receipt of theirs (`m.read`), which Synapse pushes to the matrix role with the other ephemeral events: the role keeps the instant it received the last of them, nothing else, in their own row of `owner_settings`. A private receipt (`m.read.private`) is theirs alone: the Matrix specification keeps it from an application service, as Synapse does from 1.162 on, so it counts for nothing, even where an older Synapse still pushes it, and an owner whose client sends only private receipts is seen by their messages alone. Anyone else's receipts there, their assistant's own included, and their words and receipts in any other room, count for nothing. The count goes from the day they were last seen, on their wall clock, to the brief's date, neither of them counted, so that the brief of the tenth working day goes out and the next one stops; before they were ever seen there, it starts from their first brief. The deletion of their assistant erases it, the next assistant's first brief starting the count again.

The owner also has their brief when they ask for it: their assistant calls `brief_now`, which only their own turns are offered, never a turn an event or a suggestion started, and none while `BRIEF_ENABLED` is off; the organization agent is refused. It is the brief of their date, on the wall clock of their zone, whether it is due that day or not and whether it is stopped or paused, which it leaves as it is, as it leaves the days and the time they chose. It reads as a brief does, their mail since their last brief, but tells only the meetings of the day not over yet, the one under way and the all-day ones included. It takes that date's wake-up, under the lock of the owner's wake-ups, and counts among their `WAKEUPS_PER_HOUR`, which never holds it back, so that the brief of that date goes out no more; one a pass took first stays as it is. A question or a request about their permission that their brief waits on closes as expired, and the brief asks what it still needs: the question of its reads, while it asks for them, which counts as one more time asked, or the request about their permission, when the broker refuses the day's read; a yes to either gives the brief of the rest of their day. The brief, or what it asks, is the answer of their turn, which ends there with no other model call: marked as the brief of its date, as the scheduler's is, and kept in the conversation as the call, with what the brief's numbers, its tasks' keys and its emails name as its result, and the brief as the assistant's answer. It takes what the earlier briefs named out of the conversation, as a newer brief does, and the next brief takes out what it named. Its tokens spend the owner's day as their words do, none of the share their assistant spends on its own (see Admission). The line `brief asked for` gives its date.

### Quiet hours

Each owner has quiet hours, during which their assistant posts nothing on its own: a daily range, on the quarter hour, which may cross midnight, and whole days, on the wall clock of their calendar's zone, the deployment's (`ASSISTANT_TIMEZONE`) until a read named one (see Time zone), so that they keep their times there when the clocks change. Unless they chose others, they are the deployment's, `QUIET_HOURS_DEFAULT`, from 20:00 to 08:00 and all of Saturday and Sunday by default. They hold back what the assistant does on its own alone: an owner who writes at night is answered, and their brief keeps its time. An activity that would wake the owner during their quiet hours, once their own actions and what is kept for their brief are set aside, is held instead, `quiet_hours` in their listening journal with an `activity noted` line, until it comes out of them: at their next brief, when it goes out on the day the quiet hours end (`BRIEF_ENABLED` on, a day of their brief, neither paused nor stopped), or else at their end. One about a meeting that starts before then, at its time, at the one it had for a move or at the one a counter-proposal proposes, wakes them at once. Their brief names what was held under `since_last_brief`, as it does what had no turn, and ends its hold in the transaction that keeps it (see Morning brief). At each pass, briefs on or off, the worker role's scheduler wakes the owner's assistant for what was held once its time came, the end of the quiet hours, or three hours past the brief's time for an activity that brief was to name, should it never go out: the first due first, as an event's turn, `woken` then in their journal, within their `WAKEUPS_PER_HOUR`, the rest at the next passes, with an `event queued` line each. A held activity keeps the wake-up its turn will need, as its listener cleaned it on arrival, in the owner's own rows of `held_activities` under row-level security, until a brief names it or it wakes them; one of an application they no longer listen to, or for an assistant no longer in its room, comes out of the hold and wakes nobody. The assistant's notice of a spent share is posted out of the quiet hours alone: a refusal during them posts nothing, and the first one past them posts it (see Admission).

The owner sets their quiet hours by asking their assistant, which calls `quiet_hours`: `show` reads them; `hours` sets the daily range, `start` and `end` as `HH:MM` on their wall clock, on the quarter hour, one of them kept as it stands when they name the other alone, the same time for both refused; `days` sets every whole quiet day of the week, none when empty; `none` removes both. Every call whose arguments it can read answers the quiet hours as they stand, their range, their days and the zone they follow, and every call but `show` that it accepts ends the turn on the harness's own words, which say them in the owner's language, or that there are none. What they chose is kept next to their brief, in their own row of `owner_settings`, and read at each activity. As `brief_settings` does, the tool takes the `settings.write_own` right, and a turn that comes from others, an event's or a suggestion's, is never offered it: nothing a third party writes silences or wakes the owner. The organization agent is refused. The harness refuses to start with a `QUIET_HOURS_DEFAULT` it cannot read: one range at most, `HH:MM-HH:MM` on the quarter hour, the same time for both refused, the days of the week by their English names, or `none`, which an empty value also means. The chart does not set it.

### Provisioning API

A client of the homeserver may give its user their assistant without the creator conversation: it asks a provisioner it trusts, such as the identity server it already authenticates its users with, which calls the harness on the user's behalf. The provisioner authenticates with an access token of its own OIDC client (client credentials grant, audience `AUTH_AUDIENCE`), and only the clients named in `PROVISIONER_CLIENT_IDS` (by subject) are admitted: no token or an invalid one gets a 401 `{"error":"invalid token"}`, a valid token of anyone else a 403 `{"error":"not a provisioner"}`. Behind the gateway, the shared secret is required as on the rest of `/v1`. The owner is named by their Matrix identifier, URL-encoded in the path; one that is not a user of this homeserver gets a 422 `{"error":"owner not on the homeserver"}`.

`PUT /v1/provisioning/assistants/{owner}`, with an optional body `{"timezone":"<IANA zone>"}` (the zone the owner's client reports, accepted and not kept: the harness takes each owner's zone from their calendar, see Time zone), gives the owner's assistant:

- `200 {"userId":"@<prefix><localpart>:<server>","deviceId":"<device>","masterKey":"<public key>"}` once the assistant's device is signed by its cross-signing identity. `masterKey` is the public master cross-signing key, unpadded base64, the value in `master_keys[userId].keys` of `/keys/query`: the client checks that the identity the homeserver publishes has this key, then trusts the device on it. The same answer comes back on every later call.
- `503 {"error":"not_ready"}` with `Retry-After: 5` until then. An owner without an assistant gets one at the first call, named from the locale's catalog and without a room of its own, and the matrix role makes its device and its identity at once rather than when it first speaks. That preparation is tried again by the harness itself, with a backoff, until the identity is ready, so the provisioner only needs to ask again; the matrix role also prepares every provisioned assistant at its start, room or not.
- `409 {"error":"recovery_needed"}` while the assistant's escrowed identity waits for its owner's recovery, after the matrix role lost its store: asking again changes nothing until the owner calls `POST /v1/assistants/me/recover`, or their provisioner `POST /v1/provisioning/assistants/{owner}/recover` (see Key escrow), after which the assistant's identity comes back, on a new device. A provisioner should not retry this answer: it can tell the owner, and ask for their recovery itself, the same job as the owner's route. Its call answers `202 {"queued":true}`, or `202 {"queued":false}` while a recovery of the owner's is already queued or under way; `404 {"error":"no assistant"}` without an assistant; `422 {"error":"owner not on the homeserver"}` for an owner who is not a user of this homeserver.
- `502 {"error":"assistant creation failed"}` when the homeserver refused the assistant's account.
- The answer always describes the assistant the provisioner asked for: an identity recorded for an earlier identifier of the owner's assistant, as before a change of the assistants' prefix, is never handed out.

`GET /v1/provisioning/assistants/{owner}` reads the owner's assistant without making it, so that a client learns whether its user has one without giving them one. For an assistant that exists it answers as the PUT does: `200` with its identity, `503 {"error":"not_ready"}` with `Retry-After: 5` while its identity is prepared, which it asks for as the PUT does, or `409 {"error":"recovery_needed"}`. An owner without an assistant, or whose assistant was deleted, gets a `404 {"error":"no assistant"}`: reading never creates an assistant nor brings a deleted one back.

`GET /v1/provisioning/assistants/{owner}/suggestions` answers `{"enabled":true|false}`, the owner's switch of the suggestions (see Suggestions), and `PUT` with `{"enabled":false}` or `true` turns it and answers the same: what `/v1/suggestions/settings` shows and turns, for a client whose users hold no token of the harness, such as Twake Chat. It needs no assistant, and leaves the rooms the owner muted as they are.

`PUT /v1/provisioning/assistants/{owner}/home`, with `{"roomId":"!room:server"}`, names the direct room the owner's client opened with the assistant: the room the assistant writes to its owner in, as an event's turn does, and one of the rooms it answers them in. `204` once recorded; `404 {"error":"no assistant"}` for an owner without one; `409 {"error":"not a member"}` when the assistant has not joined the room within a few seconds, or the owner is not in it; `409 {"error":"not a direct room"}` when anyone else is in it, since what the assistant writes there would reach them too.

The owner's client opens that room itself and invites the assistant. An assistant joins a room only when its own owner invites it, and the room then becomes one of its rooms, where it answers its owner as in the room it opened; the first such room becomes the room it writes to its owner in, until the provisioner names another. An assistant the provisioner made greets its owner in the first room they open with it as soon as it has joined, with the words an assistant the creator conversation greets them with in the room it opens, in their language and encrypted for their devices: once, so that neither a restart, nor the provisioner naming the room, nor inviting it again, nor a room they open with it later brings the greeting again. An assistant its owner deleted and a provisioner then made again is a new assistant, and greets them anew. An invitation from anyone else is declined and logged. The creator and the organization agent keep their own rules.

For now an assistant works in direct rooms only, its owner and itself: everyone else in a room would read what it writes its owner, their memory and their applications' data included. Invited by its owner into a room where anyone else is, joined or invited, it declines, unless that room is an encrypted conversation of the owner and one other person, which it only reads for its owner's suggestions (see Suggestions): it leaves with the reason in the owner's language, and logs it. A room where it answers its owner that someone else comes into, joined or invited, stops being one of its rooms: it says why there, leaves with the same reason, and that room is no longer the one it writes its owner in. Nothing more it would say there goes out, even when it could not leave: a message of an assistant to a room the index no longer names it in, as the answer of a turn that ran there meanwhile, is dropped with the line `send dropped: no assistant for this room`. A mode for rooms with others, without the owner's memory nor their applications, is to come (#79).

In every room of the assistant (the room it opens itself when its owner creates it, each room its owner invites it to, and the room a provisioner names) the assistant announces the commands it answers itself (MSC4332): the state event `org.matrix.msc4332.commands`, its state key the assistant's id, its content `{"commands":[{"name":"help","syntax":"help","description":{"m.text":[{"body":"..."}]}}]}` with the description in the owner's language, which Twake Chat offers after « / ». The command list lives in `src/matrix/commands.ts`. A room that already holds the same announcement is left as it is; a room that refuses the state event, by its power levels, is logged and tried again only at the next invitation or naming of it. When the owner sends `!help` (as Twake Chat sends an announced command, the command also named in the message's `org.matrix.msc4332.command` content) or `/help`, the harness answers itself, in the owner's language, without a model turn.

The creator announces its own commands the same way, as the creator, in each room it joins, before its help: `newbot`, `mybot`, `rename {name...}`, `delete`, `recover` and `help`, each described as its help describes it, in the language of the member who invited it. At each start of the matrix role, it announces them in the rooms it is already in with someone, in the background and one room at a time, in the language of the one member there, or the deployment's when there are several: the rooms it joined before it announced any, or that refused the announcement then, get it, and a room that already holds the same announcement is left as it is. It takes a command sent as `!delete`, as Twake Chat sends a command it announced, as it takes `/delete`.

In those rooms the assistant also goes by its name: its member event there carries it as `displayname`, which clients show over the name of its profile, since a homeserver may refuse profile changes, as the platform's does. A job of the matrix role writes it when the assistant joins a room, when its owner creates or renames it, and when a provisioner names its room, only where it differs and over the rest of its membership: a room that refuses it fails the job, which the queue tries again, and the greeting never waits for it. An assistant a provisioner makes takes its owner's first name, the words of their Matrix name before the first one in capitals (« Michel-Marie » for « Michel-Marie MAUDET »), else their whole name, in the owner's language and cut at 64 characters: « Michel-Marie's assistant », « Assistant de Michel-Marie », « Assistant d'Hélène » before a vowel or an h. An owner without a Matrix name, or whose name holds what an assistant's name cannot, gives their localpart instead. An assistant that goes by a name after its owner's localpart, as when the homeserver named them after their identifier, as a platform's may at their first login, takes their first name once the homeserver gives them a name of their own: each change of the owner's name comes into the assistant's rooms as a member event of theirs, which flags it and asks for its naming job. A name its owner gave it stays, « Assistant » included, and so does a name after their former Matrix name. The assistants live when the harness started naming them so went by « Assistant », or by their owner's whole name: a migration flags each of them, and the next start of the matrix role renames those still under one of these names and writes their name in their rooms, once. A name their owner gave them stays, and so does one they choose after that start, « Assistant » included; an assistant whose owner's name could not be read stays flagged for the following start.

### Key escrow

With `ESCROW_ENABLED`, the matrix role escrows each assistant's identity in the platform OpenBao, through the `openbao` route of APISIX and the Kubernetes auth method (`OPENBAO_K8S_ROLE`, the pod's projected token with the audience the chart sets): once an assistant's device is signed by its identity (see Encryption), a key backup is opened on the homeserver, and the secret storage key, the three cross-signing secrets, the backup key and its version go to `<mount>/data/<prefix>/<owner>`. The escrow only stores the keys: the identity itself is the harness's either way, and an identity replaced since is escrowed again. The database keeps the path, the master public key and the backup version only; every read and write of the escrow is logged with the principal. Room keys are backed up as they come and go. After a lost store, the escrowed identity on the homeserver is not replaced: the new device waits, and `POST /v1/assistants/me/recover` (the owner's token) or `POST /v1/provisioning/assistants/{owner}/recover` (their provisioner's, see Provisioning API) puts it back on the escrowed identity, which the owner's clients already trust, and the backup goes on; the room keys of the lost device stay in the server backup, unreadable until the crypto bindings can import them. At rest, the store on the volume is protected by the volume's own encryption (an encrypted storage class).

### Skills

Skills follow the Agent Skills format: a name, a description and Markdown instructions. Each user has a library, the organization has one, and every skill has exactly one owner. The system prompt lists the skills a user may read, with their descriptions; the model reads one with `scoped_skills_read` when it applies and searches them with `skills_search`. What the assistant learns becomes a proposal through `skills_propose`, invisible to the model until its owner approves it (`POST /v1/skills/proposals/:id/approve`). An administrator, a principal with the `skills.admin` right, writes organization skills (`POST /v1/org/skills`) and promotes a user's proposal into the organization library by copy (`POST /v1/org/skills/promote/:id`), leaving the user's library untouched. Row-level security enforces all of it: a user never sees another user's skill, and the organization's are written by administrators only.

### Session search

The model finds past conversations with `session_search`, by words they contain, among the owner's sessions only; the result gives the session ids and a snippet, and `scoped_sessions_read` opens one.

### Language

Each assistant speaks its owner's language: the one the owner chose by asking their assistant, which calls `set_language`, or else the deployment's (`ASSISTANT_LOCALE`). The model is told, in that language, to speak it, and every fixed sentence the harness says to that owner follows it: the consent questions, the acknowledgements and notices of an answer, the status of a turn that takes a while, the busy and failure notices, and the creator's replies. The choice is stored with the assistant, and kept if the owner creates it again. Changing it takes the `settings.write_own` right, which a turn an event started never holds; the organization agent speaks the deployment's language with every member. Answers to the harness's questions are understood in every language it speaks.

### Time zone

Every turn tells the model the present, right after its persona: the date and time in words, in its owner's language, the same instant in ISO 8601 with the offset of the zone at that instant, never `Z`, and the zone's name, by which it places "today" or "tomorrow" and writes the times it gives contracts. The clock is read before the model is first asked, in every turn, and never kept. The zone is the one of the owner's calendar: `list_calendar_events` and `read_calendar_event` name it in `time_zone`, as the calendar's settings give it, and the harness keeps for each owner the last one such a read returned with success, each such read refreshing it, the read their yes let run included, so that the turn this yes resumes states it already; an error answer keeps none, whatever zone it names, and a zone the runtime does not know is ignored, the one kept before staying. Until a read named one, the deployment's zone serves (`ASSISTANT_TIMEZONE`). The days of an all-day invitation the harness checks before the model speaks are those of the same zone, the owner's, or the deployment's when none is kept (see Calendar's invitations). An owner's zone is theirs alone, a row of their own under row-level security, and the organization agent keeps the deployment's. The deletion of their assistant erases it, the deployment's zone serving the next one until a read names theirs again. A read keeps it whatever turn made it, one an event started included, since it comes from the calendar's settings, which no third party writes. The zone the owner's client reports to the provisioning API is not kept, and a user's day of tokens still starts at midnight in `ASSISTANT_TIMEZONE`, whatever the zone of their calendar. The reminder of a permission about to expire counts its five days and tells when it expires in the same zone, the owner's, or the deployment's when none is kept, while its daily pass runs at an hour of `ASSISTANT_TIMEZONE` for every owner (see Consent). As the gateway's audit keeps only the path of a call, the `contract called` line of each `list_calendar_events` gives at `info` its `from` and `days`, those the call gives, as sent, so that the days the model took for "today" or "tomorrow" can be checked, and no other argument. The model writes them and the harness checks only their names, so the line gives each only once and in the shape the contract takes, a day written `YYYY-MM-DD` and a number of days from 1 to 31; it names any other in `malformedArguments`, never with what it holds.

### Contracts as tools

The harness reads the curated OpenAPI that APISIX serves and turns every operation that has an `operationId` into a tool named after it, dots replaced by underscores. A tool call goes to APISIX at the path the document gives, as OpenAPI reads it: the path of its first server, the root when it names none, then the operation's path; a server on another host keeps only its path, with a warning, since the gateway is the harness's only way out but for its database and the worker role's AMQP connection to the broker, and `CONTRACTS_BASE_PATH`, empty by default, prefixes the calls for a gateway that mounts the contracts elsewhere. It carries the harness consumer key, the contract id and the owner in `x-twake-on-behalf-of`; the gateway attaches the owner's token, so the harness never holds one. What a contract returns is handed to the model as data, status included, and every call is logged, with none of its arguments but the days a list of calendar events reads (see Time zone); the gateway writes its audit record. The catalog is loaded at start and refreshed on an interval; a failed refresh keeps the previous catalog. A write operation declares in `x-twake-risk` whether it is `low` or `high`; one that declares neither is `high`, so that a forgotten declaration asks its owner each time (see Consent), and so is one that declares anything else, with a warning logged once for its operator. A write whose contract can tell what a call would do without doing it declares `x-twake-preview: true`, and its owner sees that before they confirm the call (see Consent); any other value, and a preview a read declares, is ignored, with a warning logged once.

### Consent

An assistant reads an application only once its owner allowed it, and writes there only once its owner allowed that as well: allowing it to read never lets it write. A contract belongs to the application its id starts with (`mail` for `mail.emails.read.v1`); a `GET` contract reads, and any other method writes. The first time an assistant would read an application, or write in it, at a level its owner never allowed, the harness freezes the call as the model wrote it, stores it for its owner, and ends the turn with its own fixed question in its owner's language: nothing reaches the application but the preview of a write that offers one (see below), and nothing the model or a third party writes can phrase that question. The rights to call and to act through contracts stay above consents: an owner whose assistant may not act is refused a write as before, whatever they allowed. No consent is built in, and the organization agent, which acts for no user, never asks. Consents and waiting calls are rows of their owner, under row-level security. The assistants of the pilot kept reading Calendar when consents came, and writing there when writing asked too: every principal that could call contracts then got Calendar read, and every principal that could act through them Calendar write, so that accepting an invitation asks them nothing but whether to accept it. When reading Calendar came to cover the owner's events, private ones included, and no longer their free and busy times alone, every consent to read it was taken back, the pilot's as well as the ones owners gave themselves: each owner is asked again, in the words the contracts give then, the next time their assistant reads it, in a chat as for the availability check of an invitation that arrives. A request to read it that still waited, asked in the old words, expired, so that a yes to it allows nothing. When writing there came to cover declining the invitations an owner received as well as accepting them, a whole series included, every consent to write there was taken back in turn, the pilot's as well as the ones owners gave themselves, and a request to write there that still waited expired: each owner is asked again, in the words the contracts give then, the next time their assistant writes there. When reading Tasks came to cover the owner's projects as well as their tasks, and writing there creating projects, and assigning, commenting on and deleting tasks, every consent to read or write there was taken back, and every request to read or write there that still waited expired: each owner is asked again, in the words the contracts give then, the next time their assistant reads or writes there. When reading Calendar came to cover finding when the owner and other people are free, and writing there calling meetings, which emails an invitation to everyone invited, every consent to read or write in Calendar was taken back again, and every request to read or write there that still waited expired: each owner is asked again, in the words the contracts give then, the next time their assistant reads or writes there.

Either question names the application and says what its level, reading or writing, covers there, in its owner's language, as the catalog describes it: at the root of the OpenAPI document, `x-twake-domains` gives each domain a `name`, and what its `read` and `write` levels cover, in each language the harness speaks (`en`, `fr`), as plain words on one line (at most 64 characters for a name, 200 for what a level covers), addressed to the owner, without a final period:

```json
{
	"x-twake-domains": {
		"mail": {
			"name": { "en": "Twake Mail", "fr": "Twake Mail" },
			"read": {
				"en": "list, search and read your mail",
				"fr": "lister, chercher et lire tes mails"
			},
			"write": {
				"en": "prepare replies to your mail as drafts, which you send yourself, and move your mail between your folders, archive it or put it in the trash",
				"fr": "préparer des réponses à tes mails en brouillons, que tu envoies toi-même, et déplacer tes mails d'un dossier à l'autre, les archiver ou les mettre à la corbeille"
			}
		}
	}
}
```

A domain the document does not name in the owner's language goes by its name in the deployment's language, since a product's name rarely changes with the language, or else by its id, and what a level covers shows in the owner's language only, or not at all. The question stays the harness's own text, which the chat renders as Markdown: an entry whose words hold a markup character (``\ ` * _ ~ [ ] < > &``), anything that looks like a link, an address or a domain name, or a break of any kind is ignored with a warning, and so is an entry of any other shape, a key or a language code the harness does not know included, while the rest of the catalog loads; what goes in is escaped once more. The words are read with the catalog, at each refresh, so a new application needs no release of the harness.

The question asks for an answer in words, and carries no buttons: Twake Chat sends a reaction in the clear even in an encrypted room, so a tap on a button could never answer. Its content, encrypted with the rest of the message, also says which question it is, under `app.twake.assistant.question`: `{"id": <the request's id>, "expires_ts": <when it expires, in milliseconds since the epoch>}`, the id and the end of validity that `GET /v1/pending-calls` shows, so that a client can tell the question from other messages without reading its text, and offer both answers as words the owner sends; the text stays the same for any other client. Every question of the harness to answer yes or no carries it, the request to try again once the broker has the owner's permission, the question whether to answer for a whole series and the question of an owner's first brief about its reads included, unless its request no longer waited for an answer when the turn that asks it ended, decided from another client or closed; no other message of the assistant does. The owner answers with an exact yes or no as their next message after the question, in any language the harness speaks, or with a bare ✅ or ❌ on it from a client that encrypts its reactions; anything else they write is an ordinary message, after which only such a reaction, or an answer through the API, answers. The matrix role reads the answer itself, never the model, and only from an event that reached the assistant encrypted, sent by the owner: a reaction or a message written in the owner's name on the server, which cannot encrypt for the room, answers nothing, and an answer delivered twice answers once. A no drops the call and erases what it would have sent; the harness says so itself, without the model. A yes approves the call at once and queues a `resume` job with the owner's turns. The job grants the consent when the question asked for one, runs the call exactly as it was frozen, under the correlation id of the turn that froze it, records it in the session as the assistant's call followed by its result, erases what it sent from the waiting call, and lets the model go on, unless the call waits for its owner again, which ends the turn on the harness's new question; a resumed turn is admitted like any other.

Admission never answers a resumed turn by telling the owner to send their yes again. Refused by rate, a full queue or the platform's load, the turn waits as a turn an event woke does, tried again until `TURN_EVENT_MAX_DELAY_MS` after admission first refused it, and the call runs once admission lets it through. Refused as the owner's day is spent, or kept waiting past that delay, the call waits for an answer again, and the assistant says so on a message marked as the request, which asks it again and ends on how to answer, as any question of the harness does: a yes after midnight in `ASSISTANT_TIMEZONE` runs it when the day was spent, at once otherwise. The request counts as asked in the room from that message on, the room's latest question for an answer in words, yet supersedes no other request; delivered again, the yes that waited answers nothing. A newer request open in the room, asked while the yes waited, stays the one to answer instead: the request the yes answered closes as superseded, and the assistant says so without the marker. A request that ends before the refusal lifts closes as expired, and the assistant says why, without the marker.

Besides each application, an owner gives the platform's token broker, once, the permission for their assistant to act for them at all. When the broker has none, or the one it had expired, the gateway answers a contract call with the broker's 401, an RFC 9457 problem whose `code` is `delegation_missing` or `delegation_expired`. The call then waits for its owner, for the reason `delegation`, and the turn ends on the harness's own request, whatever the model would have said: what the call was about to do, in the application named as for a first use, why it waits, where to give that permission, and how to answer, as any question of the harness asks. The only link it shows is the broker's consent link the deployment sets in `BROKER_CONSENT_URL` (checked at start), never the `consent_url` of the answer, which a contract could write as well; without that setting, the request says why and offers to try again, with no link. The model's view of the call records that it waited for that permission. The owner's yes runs the frozen call again, once, and grants no consent; a call the broker refuses again ends the resumed turn on a new request. The organization agent, which acts for no user, reads that refusal as data.

Twake Space also needs one of its owner's API tokens, which they give on the broker's Twake Space step and which the broker holds beside that permission. A call to its contracts is refused with the broker's 401 whose `code` is `space_token_missing` while the broker holds none, with the contract's 401 `space_token_rejected` when Space no longer accepts the one it holds (expired, revoked, or of an account that left the organization), and with the contract's 403 `space_scope_missing` when that token lacks the scope the call needs, which the problem names in its `scope`. Such a call waits for its owner as for that permission, for the same reason `delegation`, and its request tells why: no token given yet, one Space no longer accepts, or one short of a permission, named in Space's own words for `space:read`, `space:write`, `members:write` and `feed:read`, and in general words for any other scope, which the request never shows. Its link is the same consent link, opened on the broker's Twake Space step (`app=space`). Each code is a refusal only with its own status; the model reads any other answer as data.

Five days or less before that permission expires, its owner reads so in their assistant's room. Every day at `DELEGATION_REMINDER_HOUR`, 9 by default, on the wall clock of `ASSISTANT_TIMEZONE`, the worker role asks the broker, one owner after the other, what it holds of the permission of each owner whose assistant is in its room: a `GET` of `delegation` under `APISIX_BASE_URL` and then `CONTRACTS_BASE_PATH`, naming the owner as a contract call does. The gateway must publish the broker's route there: at its root, `/delegation`, for a harness whose `APISIX_BASE_URL` ends in `/b2b/` and whose `CONTRACTS_BASE_PATH` is `..`. The worker role asks during that hour only: a pass that fails runs again within it, and a role that starts after it, or whose pass fails throughout it, waits for the next day's, which misses nobody, a permission being reminded of from five days before it expires. An owner whose permission has not expired, and expires within five days of the calendar, as the zone of their calendar counts them (see Time zone), reads when it expires, on the wall clock of that zone, and where to renew it: the consent link the deployment sets in `BROKER_CONSENT_URL`, bound to them as any consent link the harness shows, never the `consent_url` of the broker's answer. Without that setting, the worker role reminds nobody, and its line `delegation reminders off` says so once at its start. The reminder asks nothing, and nothing waits for an answer. It goes out once for each date the owner gave their permission, kept with the message it queues in place of the one kept for the permission before, so that the harness keeps one by owner at most: a pass that runs again, after a restart or on another replica, reminds nobody twice, and the permission they give next is reminded of in its turn. An owner of whom the broker holds no permission, which it answers with a 404 whose `code` is `delegation_missing`, or an expired one, is reminded of nothing, and no line says so. Nor is one the broker could not be asked about, and the pass goes on with the next owner: any other 404 is the gateway's, which publishes no route there, and the warning `delegation route missing` names the path asked; a broker that fails or does not answer within `CONTRACTS_TIMEOUT_MS` gets the warning `delegation reminder skipped`.

A calendar contract answers an invitation that repeats, or whose copy holds several occurrences of a series, only for the whole series, once the owner said so: a call that accepts or declines one without `series` set to true in its body gets a 409, an RFC 9457 problem whose `code` is `recurring_invitation`, and nothing is written. A copy that holds one occurrence alone is answered as an event, `series` or not, and an invitation whose event the organizer cancelled gets a 409 whose `code` is `invitation_cancelled` before the series is checked, which the model reads as data, with no question about a series. The model cannot answer for a whole series itself: from every new call for an owner to a contract whose body takes `series`, the model's or a direct one through `POST /v1/tool`, the harness takes `series` out of the body, whatever its value, so that only the owner's yes to its question sets it. When the contract's body takes `series`, a refusal whose `code` is `recurring_invitation` ends the turn on the harness's own question, whatever the model would have said. The call for every occurrence, its body's `series` set to true, waits for its owner, for the reason `series`, and is asked about as any call that waits: the request shows what the model wrote alongside the call, quoted, the question whether to answer for the whole series, in the application named as the catalog does, that call, whole, or, when the application offers a preview, what it says the call would do in its place, whose digest the call then carries, and how to answer; the conversation keeps that call in place of what the application said, for the model's later turns. The model's view of the call records that it waited for that answer. The owner's yes runs that call the usual way of writes, and grants no consent: at once when nothing else holds it, and otherwise once they answered, on a request of its own, what else a write waits for, such as a first write in the application, or a write a turn an event started prepared, which asks each time, even once they let their assistant write there; their no drops it, and nothing is written. That call keeps `series` through a request for the broker's permission that may follow, whose yes asks nothing about the series again, whether the broker refused that call or, after the owner's yes to the series, the preview of a request that still applies, such as their consent to a first write. A call whose preview for the question about the series the broker refuses, before that yes, waits for that permission without `series`: once the owner gave it, the contract refuses the call for one occurrence again, and the question comes then. A contract whose body does not take `series`, a call for the whole series it refuses all the same, and the organization agent, which has nobody to ask and whose calls keep the `series` they set, leave the refusal to the model, as data.

A question expires after `CONSENT_REQUEST_LIFETIME_MS`, a day by default, asked again by a refused yes or not, and a newer question in the same room supersedes it: an answer to either runs nothing, and only the first answer gets a notice; what the call would have sent is erased. Every hour, the worker role expires the questions nobody answered.

The creator asks the same way before it deletes an assistant. `/delete` deletes nothing yet: it asks the owner, in their language, to confirm the deletion of the assistant it names, saying what the deletion erases, and marks that question with an id of its own, which no pending call shows, and an `expires_ts` ten minutes after it asked; without an assistant, it answers as before and asks nothing. The owner's next message answers: an exact yes, in any language the harness speaks, deletes that assistant, and any other message, a command, an image or a file included, keeps it, the creator saying the deletion is cancelled. The question stands for the ten minutes, and only while the assistant it named is the owner's: once they are over, or once that assistant is gone, deleted through the API for instance, even if the owner created another since, a yes or a no deletes nothing and is told so, with how to ask again, while anything else is read as if nothing had been asked. The creator takes the answer as it takes any command (see The owner's sessions): a reaction on its question answers nothing, and the question takes one answer: of two that reach it together, the same one delivered twice included, the creator acts on the first and says nothing of the other.

A deletion, by that yes or by `DELETE /v1/assistants/me`, which asks nothing, erases what the harness keeps of the assistant, under its owner's principal and in one transaction: the owner's sessions, its memory, their skills and the ones it proposed, their consents, the calls that wait for their answer, the suggestions it made them (see Suggestions), the brief that waits for their answer, the question of their first brief, whether their brief still asks for its reads, when they were last seen in its room and what they chose of their brief, its time, its days, a pause or a stop (see Morning brief), the zone of their calendar (see Time zone), the activities their quiet hours hold (see Quiet hours), the reminders of their delegation, what it told them of their sessions and the question it asked them about their identity, with their answer. So go the jobs that would still run for it, the owner's turns, queued or deferred, an event's included, the suggestions it was still to make, with the messages they quote, those that would show its name, and what it was to send, and those of theirs that failed for good, whose content may quote their words; another owner's jobs stay. A turn that runs through the deletion keeps nothing: what it would keep in its conversation's name, a note, a proposed skill or a call that waits for the owner, finds the conversation gone, and its answer, which would go out as an assistant that left the room, goes nowhere. Nor does a turn of a room that waited for the owner's turn before it: it opens no conversation once the assistant no longer answers there, and a deletion that comes while it opens one waits for it, then erases it too. The assistant first leaves every room it is in: those it answered its owner in, the rooms they opened with it included, and any other the homeserver lists for it, such as a room it could not leave once someone else came in. Should the homeserver refuse, nothing is erased: the line `assistant not deleted: a room was not left` names the room, and the owner, told their request failed, may ask again. Its record stays, marked deleted, with the language its owner chose. What a new assistant needs or must not lose stays: its Matrix account, device and keys, as a Matrix identifier is never reused; the owner's quota counters, so that a deletion never gives a spent day back; whether they want suggestions and the rooms they muted, which they chose for themselves; the identity the harness pinned for the owner, and the one it saw last; the wake-ups, an event id and a date each, and the owner's listening journal, until its purge, so that an event replayed within their retention wakes no new assistant, and that the next one has no second brief of a date that had one; and, likewise, the owner's words it received and when it first read each session they came from, so that a copy of their words, or the words of a session older than those it remembers, count no more for the next assistant than for the one before. The gateway keeps its audit. An assistant created again takes the same Matrix identifier, with nothing of the one before, greets its owner in a new room, tells them there again what it would say of a session of theirs, asks them there again about an identity of theirs it does not know, and reminds them, five days or less before it expires, of the permission they give again for it to act for them, since the deletion revokes the one before.

A deletion also asks the broker to revoke that permission, by a `revoke` job the same transaction queues once the owner's jobs are erased, which no erasure of their jobs takes, that of their next assistant included: the deletion never waits for the broker. The matrix role runs it through the gateway, naming the owner as a contract call does: a `GET` of `delegation`, as the reminders ask, then a `DELETE` of the same route, which the gateway must publish beside it. The broker erases the permission, if it holds one, then leaves the owner's Drive instance, and answers with a 204: the line `delegation revoked` says so. A permission the broker dates after the owner asked for the deletion when a try asks, one they gave again since, stays, with the line `delegation kept: given again since the deletion`; one they give between that `GET` and the `DELETE` that follows it is revoked. One the broker no longer holds, a 404 whose `code` is `delegation_missing`, is revoked all the same, as a try whose Drive instance did not answer erased it before the broker could leave the instance. A broker that fails, such as its 502 `drive_unavailable` when that instance does not answer, or does not answer within `CONTRACTS_TIMEOUT_MS`, and a gateway that publishes no route there, any other 404, fail the try: the queue tries again a minute later, then after ten minutes, an hour, six hours and a day, and gives up after the sixth try, about a day and a half after the deletion, where any other job gives up after its third, within seconds. Each failed try is logged as `job failed`, of kind `revoke`, with why. So a revocation outlasts an outage of the broker, of the gateway or of the owner's Drive instance, and a gateway that publishes the route only after the harness starts. The revocations of one owner run one at a time, in the order of their deletions.

The owner asks their assistant what it may access, and the model answers from `consents_list`: each application and level the owner allowed, how and when. The owner tells it to stop using an application, or only to stop writing there, and the model calls `consents_withdraw` with the application and, for writing alone, the `write` level: the next call there asks the owner again, on every replica at once, since every check reads the database. A name the catalog does not offer is refused, with the applications it does offer, unless the owner had allowed it before the catalog dropped it. The withdrawal also closes the questions still open there and the calls the owner allowed that have not run yet, as a newer question closes an older one: an answer to such a question gets the notice, and nothing runs there after the withdrawal. No tool grants a consent; only the owner's own answer does. Withdrawing takes the `consents.withdraw_own` right, which every principal that can chat holds and a turn an event started never does: an event's text cannot make the assistant withdraw anything. In the owner's own turns, text the assistant reads, a mail for instance, could still lead it to withdraw a consent, which only makes it ask again. The organization agent, which holds no consent, neither lists nor withdraws one.

A high-risk write, one that sends words to other people in the owner's name, shares or publishes, deletes for good, or trains what other users share, waits for its owner every time, whatever they allowed, and runs only once they confirmed that very call. One request asks about every reason a call waits for, but the broker's permission and the whole series, which each come on a request of their own, so that a first write that answers for a whole series asks twice: the first high-risk write in an application asks once, and its yes both allows writing there and confirms that call, whereas a yes that only confirms a call allows nothing more; should its owner take writing back before they confirm, the call waits again, asking for both, and the request they answered is closed as superseded, as it is when the broker refuses a call again.

A turn an event started reads as any turn does, its first read of an application asking as it would in a conversation, but every write it prepares waits for its owner, whatever they allowed, since what arrived was written by someone else: what the model wrote alongside the call, quoted in the request, carries the event's context. The owner's yes runs that very call and nothing more. The turn it resumes is still the event's, as if it had never stopped: any other write it prepares asks again, and it never changes how the assistant speaks to its owner, keeps a note or a skill proposal, or withdraws a consent, which only the owner's own turns do. A write that is also the first in its application asks both in one request, whose yes also allows writing there.

A request about a first use, a high-risk write or a write that a turn an event started prepared shows, in order: what the model wrote alongside the call, quoted under the harness's label ("Your assistant wrote:"), at most 2,000 characters of it; the harness's question, which names the application and, for a first use, says what the level covers there; the call itself, whole, as the model wrote it, in a code block, or, for a write that offers a preview, what its application says it would do, in its place, quoted under the harness's label ("Twake Mail describes it as:"); and how to answer. A first read shows no call: its question asks only whether its owner allows the assistant to read in the application, and says what reading covers there, since their yes lets it read there whatever it reads. A write the model wrote without arguments never shows its owner an empty `{}`: unless a summary stands in its place, a first write shows no call, its question asking only whether its owner allows it, since it already says what writing covers there, and a question about that very call, a high-risk write's or an event turn's, shows the tool it calls instead, as the harness names it. The harness lays the message out itself, as plain text and as HTML. What the model wrote renders its Markdown, held whole in the quote under the harness's label, every tag of it closed within it, but with nothing that acts, since Twake Chat opens a link on a touch without asking and a received mail may have phrased those words: none of its HTML, a link as its text alone, an address or an e-mail address as text, an image as its description, which no client then fetches from another server, and a heading as a paragraph. It shows as its lines of text should its rendering take more of the event than those escaped lines could, 12,000 bytes, and the plain text quotes it line by line. The question renders from the harness's own Markdown, and the call or its application's summary, which may hold what a third party wrote, shows as code: nothing the model or a third party wrote passes for the harness's words. An owner is never asked about a call they cannot see whole: a call, or a summary, that would take more than 16 KiB of the event that carries the request, as plain text and as HTML together, escaped as the event's JSON holds them, waits for nothing, and the model reads that it is too large to confirm, so that it may make it smaller; a first read, which shows none, never is. With the model's words, 12,000 bytes at most in each, the largest request stays under 60 KiB once encrypted, well within the 64 KiB a Matrix event may take. A request travels in its parts, the question apart from the call, and the API answers a turn with its plain text. The conversation keeps the request for the model's later turns as its owner read it, with the call as the model wrote it in place of what an application said of it: that is the application's data, which may hold what a third party wrote, possibly from an application the owner never let the assistant read, and only the owner reads it, in the request itself, which the harness stores nowhere else. A first read is kept as its owner read it, without a call, and a call without arguments without an empty one: what would run comes just before the request in the conversation, as the model's own call or, for the harness's own check of an invitation's slot, in what the model is told; but where its owner read a summary, the conversation shows the call as the model wrote it, `{}`, as it does for any call with a preview.

When the application can tell what a write would affect, such as the recipients a mail would reach or the item it would delete, its owner sees that rather than the call the model wrote. Before it asks about a write whose operation declares `x-twake-preview: true`, the harness calls the contract as the call would go, same method, path, query and body, in the owner's name and under the correlation id of the turn, with `x-twake-preview: true` and the owner's language in `accept-language`. The contract answers what the call would do, and does nothing: a `200` that carries `x-twake-preview: true` back in its own headers, whose JSON body holds a `summary`, plain text for the owner, on several lines if need be, without any control or format character but line feeds and tabs, and a `digest`, an opaque token of 1 to 256 letters, digits or `+ / = . _ : -` that covers what the call acts on:

```json
{
	"summary": "To: Paul Martin <paul@example.com> and the 3 members of finance\nSubject: Q4 budget",
	"digest": "sha256:4f1c2e9a"
}
```

The request shows the summary in the call's place, as data, as it would show the call. Only a write that declares the preview is ever called so, and only to ask its owner: a contract that never promised a preview would take that call for the action itself, and a read before its owner allowed it would read their data. The harness keeps the digest with the frozen call, and the call its owner allowed carries it in `x-twake-preview-digest`, never `x-twake-preview`. A contract that finds what the call acts on changed since answers `409` and does nothing: the harness then tells the owner itself that the action was not done, without the model, which reads in the conversation the call, the contract's answer and that notice. The digest is erased with what the call would send once the call is decided, and the harness logs neither it nor the summary; the gateway's audit records the digest an allowed call carries, which ties that call to the preview its owner saw.

Any other answer to a preview asks the owner nothing. A preview the broker refuses for want of the owner's permission asks for that permission, as a refused call does, and the call is previewed once it may be. Any other success is taken for the call itself, done, since a contract that ignores the header answers that way: the turn ends on the harness's own notice that the application did the action without waiting for the owner's yes, the model reads that the call was made, with the status of the answer and never its body, which may hold a summary meant for the owner, the operator reads an error, and the replica stops previewing that contract until its catalog loads again, so that no other preview there acts. An error, which the model reads to fix the call or tell its owner, and no answer in time, after which the model reads that whether the application did anything is unknown, leave the contract previewed, and the operator reads a warning that says what was wrong, never what the contract answered.

With their own token, and under their own rights as on the other owner routes, `chat` to read, grant and answer and `consents.withdraw_own` to withdraw, an owner manages their consents through the API, as a settings page would: `GET /v1/consents` lists them; `PUT /v1/consents/{application}/{level}` grants a level the catalog offers (201, or 200 when it was given already), and `DELETE /v1/consents/{application}/{level}` withdraws one (204, or 404 when there is none). A turn through `POST /v1/chat` that stops on the harness's question answers with the whole request, as the room shows it, and returns the call it froze as `pending_call` beside it, and a direct call through `POST /v1/tool` answers 202 with that call instead of running; a pending call shows the question alone. `GET /v1/pending-calls` lists what waits for the owner's answer, asked in their room (`room`), in a turn through the API's chat (`api_chat`) or by a direct call through its tool route (`api_tool`): its id, application, level, reasons, the harness's question with what the application and level cover there, and when it expires, never what the call would send nor the model's words alongside it. `POST /v1/pending-calls/{id}/approve` answers yes: a call asked in the room resumes there as after a ✅ (202), a turn through the API goes on and answers as `POST /v1/chat` does, admitted like any turn, the call still waiting if the turn is refused, and a direct tool call runs and answers as `POST /v1/tool` does, under the owner's rights at that moment; the consent a yes to a first use grants is recorded as given through the API. `POST /v1/pending-calls/{id}/refuse` answers no, and in the room the harness says so as after a ❌. An answer through the API is recorded under an id of its own, `api:` and the request's id, as one in the room is under its event's, so that the first answer wins, in the room or through the API, however close they come: a later one through the API gets a 409 with the call's state, and a later one in the room changes nothing. A yes through the API runs a call of a turn through the API, or of a direct tool call, at once, with no job behind it: should its replica die before the call runs, the owner's next yes runs it once the lease a replica holds a job for, fifteen minutes, has passed, and gets a 409 before. Another owner's consents and calls stay out of reach under row-level security: the routes answer 404.

Each role counts on its own `/metrics` what it does of consent, by application (`domain`), `level` and `reason`, never by owner, room or argument; a call that waits for several reasons counts once, under all of them joined by `+`. The api role counts the calls it freezes, `harness_consent_requests_total`, the question of an owner's first brief under the domain `brief`, and the calls it runs once their owner allowed them, `harness_consent_replays_total`, whose `outcome` is `ok` when the application answered with a success and `failed` otherwise. The matrix role counts the owners' answers in the chat, and the api role those given through it, `harness_consent_answers_total`, by `answer` (`yes` or `no`), `via` (`reaction`, `words` or `api`) and `outcome`: `decided`, or `expired` or `superseded` for an answer that came too late and ran nothing. It also counts the questions a newer one superseded, `harness_consent_supersessions_total`, which the api role counts too for the questions and calls a withdrawal closes, and those an answer found past their lifetime, `harness_consent_expiries_total`, in which the api role counts those it finds too, and the questions a brief gave way to or asked in its place that the next brief to go out, or the brief that stops for want of an answer, closes unanswered (see Morning brief), and the worker role the questions its hourly pass expires. A counter shows once it counted, and, like every counter of `/metrics`, is its replica's own: a dashboard sums it over the replicas of the role. A replay or a frozen call retried after a failed commit may be counted twice, by the replica that retries it.
